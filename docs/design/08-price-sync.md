# 商品多级阶梯价格与同步重算

## 配置和计价

Excel 模板和导入流程不增加字段。商品导入成功后，在商品编辑器逐个设置阶梯；不开启时使用普通 `casePrice`，开启时完全使用阶梯表。第一档固定 1 箱起，箱价独立填写，首次开启默认填入普通箱价；后续修改普通箱价不改变第一档。第一档可高于、等于或低于普通箱价，须大于零且最多四位小数。手动增加或删除后续优惠档位，每商品最多 100 档优惠（含第一档共 101 行）；后续起始箱数为 2～999999 的递增整数，箱价须逐档降低。下一档起始箱数减一是本档上界，最后一档不设上限。

每个商品统一选择一种模式：

- `WHOLE_ORDER`：根据本张订单该商品总箱数，全部箱数使用最高已达档位的箱价。
- `INCREMENTAL`：各段分别计价，起始箱计入新档。例如 500 箱起优惠，前 499 箱为基础价，第 500 箱开始为优惠价。

基础价 300、500 箱起 290、1000 箱起 280 时，1200 箱整批为 336000；分段为 `499×300 + 500×290 + 201×280 = 350980`。金额用 BigDecimal 计算，最终保留两位；各段按累计舍入分配金额，确保明细合计等于商品小计。H5 和后台试算使用相同边界及整数精度算法。

更新请求传顶层 `priceTiers` 完整数组（第一行 `minQuantity=1`）及 `priceTierPricingMode`；空数组清除并恢复普通箱价，省略保持现有规则。旧单档 `priceTierSet/priceTierMinQuantity/priceTierCasePrice` 和不含第一档的旧数组请求继续兼容，保存时以本次普通箱价补足独立第一档。响应 `priceTier.tiers` 返回完整规则；旧 `minQuantity/casePrice` 描述第一优惠档，仅有第一档时返回该档。订单已命中阶梯字段仍只记录 2 箱及以上的优惠门槛。

金额试算继续保留，使用编辑页当前规则在浏览器本地计算，不新增接口请求。仅修改普通箱价、且独立阶梯规则未变时，不触发已有订单重算。

## 方案一：保存时同步完成

商品规则、当前有效订单和汇总在同一事务提交，完成后接口才返回成功；没有独立后台重算任务。

1. 锁定活动行，读取商品当前版本；以商品锁版本防止覆盖其他管理员修改。
2. 查询本活动、同商品 ID、`SUBMITTED` 的当前订单明细，使用完整规则计算，仅记录实际变化。
3. 每批至多 200 条。修改前仅冻结本次变价商品尚未持久化的提交明细；已存在的版本快照保持原样。
4. 批量写入当前明细的价格、计费段快照和金额；订单总额增加本商品新旧金额差，同时增加内部锁版本并更新时间。
5. 已完整的商品线汇总按本商品金额差额更新；仅缺失或标记为需重建的汇总执行完整重建。批量写 `ORDER_PRICE_UPDATED` outbox 事件，末尾按既有机制刷新最终展示快照。
6. 与商品目录版本及变更通知一起提交；任一步失败全部回滚。相同规则重存不写订单、统计和订单事件。

批处理仅减少数据库往返，**每批不提交，不释放活动锁**。其他活动、撤回/作废订单不参与；不改变数量、吨数、首次/最后提交时间、提交版本号或其他商品属性，不新增 `order_version` 或 `order_operation`。原有商品保存审计继续保留。

订单总额和商品线统计按差额更新，避免逐单扫描全部商品重新求金额。`(activity_product_id,order_id)` 索引定位受影响明细；历史只冻结变价商品，例如 3000 单、每单 180 商品、只调一个商品时，冻结约 3000 行而非 54 万行。缺失/需重建的汇总仍需扫描订单全量明细。

## 下单与展示

下单、管理员改单与商品调价沿用相同活动锁顺序。订单写事务使用 `READ_COMMITTED`，等待保存提交后重新读取最新规则。保存期间同活动下单可能等待；不能把“同步完成”理解成“没有等待”。性能记录见[多级阶梯验证](../testing/multiple-price-tiers-2026-11-01.md)。

商品目录缓存按既有事务后通知更新完整阶梯。H5 不增加商品轮询、即时推送或提交前确认请求；已打开的购物车继续按本页已加载规则试算，提交成功展示服务器最终金额。已提交订单页按既有进入/手动刷新等时机读取最新金额，编辑中的箱数不会被覆盖。

`order_item.pricing_details` 和 `order_version_item.pricing_details` 保存完整规则与各实际计费段；当前订单、历史详情、后台改单和导出均使用自身快照。无阶梯/旧记录可为空，前端继续使用旧字段兼容展示。导出保留原列顺序并追加“各档计费明细”；多档分段的单一阶梯价/门槛列注明“多档，见计费明细”。

当前提交版本沿用延迟冻结：历史读取以已冻结行覆盖同一行号的当前明细，其他未改行仍投影当前明细。产生下一提交版本、后台改单或其他需要完整冻结的写入前，补齐尚未冻结的全部行；因此旧版本独立完整，后续不会回读新版本的商品。直接对当前版本的物理 `order_version_item` 求和不代表完整历史，应使用版本读取接口。

H5 当前订单、后台订单详情及版本读取使用一致的只读事务快照，避免调价或提交并发时混合不同时间点的行。既有订单版本/状态冲突继续返回 409。

## 实现边界与迁移

- `TierPricing`：完整档位和计费段类型、JSON 快照。
- `OrderPricingCalculator`：整批/分段纯计算和金额比较。
- `ProductService`：规则校验、保存及触发同步；`ProductCatalogReader` 合并所有档位。
- `PriceSyncService/Repository`：定位变化、历史冻结顺序、批量更新与事件。
- `OrderRepository`：公共活动锁、按商品冻结/完整补齐、历史合并和订单读写；`DashboardSummaryStore` 维护金额差额及缺失汇总重建。

V047 将阶梯唯一约束改为商品 ID + 起始箱数，旧单档直接保留；新增两处 JSON 快照及商品定位索引。V048 将商品阶梯起点约束放宽到 1，为已有阶梯商品补入原普通箱价作为第一档，并递增受影响活动的目录版本；不修改已有订单和历史金额。订单的优惠命中门槛仍至少为 2。源码未自动迁移业务库，部署时须先备份并按既有 Flyway 流程应用迁移，再切换新版前后端。

吨箱转换系数同步沿用独立 `TonnageSyncService`，不改变本次金额规则。原补处理入口 `PRICE_SYNC_BACKFILL_ACTIVITY_ID` 默认关闭，只校正指定进行中活动；本次不自动执行。旧 `price_sync_batch` 表保留兼容，不作为后台任务队列。

自动调价不新增提交版本；管理员主动调整仍由订单服务和 `OrderRepository.saveRepriced` 维护新版本及操作记录。
