# 部门账号与多活动隔离开发任务清单

> 状态：核心代码已实现，待预发布双部门验收  
> 确认日期：2026-09-02  
> 目标：一个部门一个共享后台账号；同部门同一时间只能发布一场活动；不同部门可同时发布，且后台、H5、看板和抽奖数据互不串联。

## 1. 已确认规则

- 后台仍使用同一个登录页和同一套管理系统，不建设第二个网站。
- 保留一个 `SUPER_ADMIN` 超级管理员；超级管理员可以管理部门、部门账号和全部活动。
- 每个部门最多绑定一个有效的 `DEPARTMENT_ADMIN` 部门账号；部门内人员共用该账号。
- 部门账号只可查看和操作本部门活动及其业务数据，不能管理部门或其他账号。
- 新建部门账号时由超级管理员设置 8-100 位初始密码（至少 8 位，超过 8 位均可），首次登录强制修改密码。
- 每场活动必须归属一个部门；部门账号新建活动时由后端自动绑定当前部门，不能由前端指定或修改归属。
- 创建“默认业务部门”，编码为 `DEFAULT`，并将全部存量活动（包括当前进行中的活动）迁入该部门。
- 新建部门时由服务端根据部门名称生成唯一部门编码；编码创建成功后固定，部门名称后续修改不影响编码。
- 当前管理员账号迁移为超级管理员；迁移过程不改变现有活动 ID、活动编号、订单、H5 地址、看板或抽奖数据。
- 同一部门的两场已发布活动，其完整活动时间不得重叠；不同部门不做时间冲突限制。
- 完整活动时间按 `[starts_at, COALESCE(event_ends_at, ends_at))` 计算；首尾相接不算重叠。
- 草稿、已撤回发布和已结束活动不占用发布时间；待开始、进行中以及订货截止但整场尚未结束的活动占用时间。数据库中的 `ARCHIVED` 仅为兼容状态，不作为当前正常归档流程。
- 每场活动使用独立 H5、看板、排行和抽奖地址，并以 `activityCode` 作为入口标识。
- 部门共享账号的审计只能识别到部门账号、IP 和会话，不能识别部门内部的具体操作人，这是本方案接受的限制。

- [x] 插入“默认业务部门”（`DEFAULT` / `默认业务部门`）；通过唯一部门编码和 Flyway 版本控制保证不会重复创建。

- [x] 登录时拒绝已停用部门下的部门账号，即使账号自身仍为启用状态。
- [x] 保留首次登录强制改密流程。
- [x] 修改密码、重置密码、禁用账号或停用部门时，撤销该账号的现有后台会话。
- [x] 增加统一的角色判断：`requireSuperAdmin`。
- [x] 增加统一的数据范围判断：`requireActivityAccess`、`requireDepartmentAccess`。
- [x] 越权访问其他部门资源时统一返回 404，避免泄露资源是否存在。
- [x] 审计登录成功、登录失败、改密、重置密码、启停账号和启停部门；不得记录明文密码或会话令牌。

## 5. 后台数据权限隔离

- [x] 超级管理员活动列表可查看全部部门，并支持按部门筛选。
- [x] 部门账号活动列表强制增加当前 `department_id` 条件。
- [x] 部门账号创建活动时，后端从登录身份写入部门，不接受请求体中的部门 ID。
- [x] 超级管理员创建活动时必须选择所属部门。
- [x] 活动详情、修改、发布、撤回、截止和结束均执行活动访问校验。
- [x] 商品、商品图片、白名单、到场名单、导入、订单、导出、抽奖、看板和审计接口均执行活动访问校验。
- [x] 只携带 `fileId`、`taskId`、`orderId`、`ruleId`、`roundId` 等子资源 ID 的接口，必须反查所属 `activity_id` 后再鉴权。
- [x] 全局审计日志仅超级管理员可访问；部门账号只能读取本部门活动日志。
- [ ] 文件对象键继续包含活动 ID；下载文件时校验文件所属活动的数据权限。
- [ ] 对所有 `/admin/**` 接口完成一次资源归属清单审查，避免遗漏无 `activityId` 路径参数的接口。

## 6. 同部门活动发布时间冲突

- [x] 将当前全局时间冲突检查改为同部门检查。
- [x] 发布事务内先锁定所属 `department` 行，再执行冲突查询和发布更新，防止同部门并发发布同时成功。
- [x] 冲突条件使用半开区间：`other.starts_at < current_end AND other_end > current.starts_at`。
- [x] 冲突查询仅包含占用发布时间的已发布活动，并限制 `other.department_id = current.department_id`。
- [x] 不同部门发布时锁定不同部门行，允许真正并发，不再锁定全部活动。
- [x] 发布、调整待开始活动时间、延长进行中活动、修改整场结束时间和撤回后重新发布时都重新检查冲突。
- [x] 冲突响应使用 `DEPARTMENT_ACTIVITY_TIME_CONFLICT`，返回冲突活动名称、编号和时间，便于管理员处理。
- [x] 撤回发布或整场结束后释放该部门对应时间段。

## 7. H5 入口与客户会话隔离

- [x] 正式入口统一为 `/h5/{activityCode}`，每场活动生成独立链接和二维码。
- [ ] 通用 `/h5` 不再调用“全系统唯一当前活动”；改成扫码提示或活动选择页。
- [x] `/public/activities/current` 不再作为多部门正式入口依赖；如保留，必须明确其兼容用途。
- [x] 手机号验证严格使用目标活动自己的白名单。
- [x] H5 会话继续绑定 `activity_id`、活动客户 ID 和客户类型。
- [x] 每次读取商品、草稿、订单、撤回或提交时，校验 URL 活动与 H5 会话活动一致。
- [x] 明确同一浏览器同时打开两场活动时的体验：本期可保持“最后一次验证的活动会话生效”，但必须返回清晰的活动身份不匹配提示，绝不能回退到其他活动数据。
- [x] 活动撤回、结束或白名单身份失效时，只撤销该活动对应的 H5 会话。

## 8. 看板、排行、战报和抽奖隔离

- [x] 每场活动生成独立地址：`/screen/{activityCode}/dashboard`、`ranking`、`report`、`lottery`。
- [x] 看板统计、排行、战报、抽奖规则、候选池、轮次和中奖结果的所有查询都必须包含 `activity_id`。
- [x] 看板快照继续使用 `(activity_id, snapshot_key)` 唯一键。
- [x] 缓存键统一包含活动 ID，例如 `activity:{activityId}:dashboard`，禁止使用全局 `current`、`latest` 类业务键。
- [x] SSE/实时事件订阅和发布继续按 `activityId` 分组。
- [ ] 如生产环境部署多个后端实例，使用 Redis Pub/Sub 或等价机制广播按活动分区的失效事件，避免某实例消费 outbox 后其他实例的客户端收不到通知。
- [x] 抽奖互斥键至少包含活动或全局唯一轮次 ID，并校验轮次所属活动，避免传入其他活动轮次。
- [ ] 为看板增加绑定活动且可撤销的 `screenToken`；令牌校验失败不得返回活动统计或抽奖结果。
- [x] 活动结束后保留该活动自己的历史看板和战报，不合并其他部门数据。

## 11. 自动化测试与验收

### 11.1 账号和权限

- [ ] 超级管理员可以新增部门和部门账号。
- [ ] 部门账号不能访问部门、账号或全局审计管理接口。
- [ ] A 部门账号只能列出和操作 A 部门活动。
- [ ] A 部门修改 URL、活动 ID 或子资源 ID 后，不能读取、修改、导出或下载 B 部门资源。
- [ ] 禁用账号、停用部门或重置密码后，旧会话立即失效。

### 11.2 活动冲突

- [ ] 同部门完全重叠、部分重叠和包含关系的第二场活动均发布失败。
- [ ] 同部门活动首尾相接可以发布。
- [ ] 不同部门时间完全相同可以同时发布。
- [ ] 同部门重叠草稿不阻塞发布；撤回后释放时间。
- [ ] 订货截止但整场未结束的活动仍阻塞同部门重叠发布。
- [ ] 延长活动造成冲突时修改失败。
- [ ] 两个同部门并发发布请求只成功一个；两个不同部门请求都能成功。

### 11.3 全链路防串

- [ ] A/B 两场同时运行时，H5 活动信息、白名单验证、商品、草稿和订单互不串联。
- [ ] A/B 看板统计、排行、战报、快照和实时消息互不串联。
- [ ] A/B 抽奖规则、候选池、轮次、中奖结果和重置操作互不串联。
- [ ] A/B 文件、导入任务、导出文件和审计记录互不串联。
- [ ] 使用错误活动的 H5 会话、screen token 或资源 ID 时不返回任何目标活动数据。

### 11.4 存量活动迁移

- [ ] 迁移后存在且仅存在一个 `DEFAULT` 部门。
- [ ] 所有存量活动均绑定默认业务部门，不存在空 `department_id`。
- [ ] 当前进行中活动的 ID、编号、状态、时间和数据量迁移前后一致。
- [ ] 原 H5 活动地址仍可访问，现有订单、看板快照和抽奖结果数量一致。
- [ ] 当前管理员可以超级管理员身份登录。

## 12. 上线步骤与完成定义

- [ ] 备份生产数据库，并完成恢复演练。
- [ ] 在预发布环境复制生产数据并执行迁移、回归和双部门并发活动演练。
- [ ] 先发布兼容新旧字段的后端，再启用非空约束和新前端，避免滚动发布期间字段不兼容。
- [ ] 生产迁移后核对默认部门、账号角色、活动数量及主要业务表按活动的数据量。
- [ ] 由超级管理员在页面中创建真实部门和部门账号；默认部门账号不在迁移中自动创建。
- [ ] 在需要时将活动从默认业务部门调整至真实部门；正在进行中的活动调整必须审计。
- [ ] 用两个部门账号同时完成发布、H5 下单、看板刷新和抽奖验收。
- [ ] 验收通过后关闭或明确标记旧的全局 `/h5` 自动活动入口。

以下条件全部满足后，本任务才算完成：

1. 部门账号无法通过任何后台接口访问其他部门数据；
2. 同部门重叠发布在普通请求和并发请求下都被阻止；
3. 不同部门活动可以同时运行；
4. H5、看板、排行、战报、抽奖、缓存和实时消息均通过交叉测试确认不串；
5. 当前进行中活动无损迁入默认业务部门；
6. OpenAPI、数据库结构、权限文档和自动化测试与实现保持一致。
