# 权限、并发、幂等、安全与审计设计

## 1. 权限模型

当前使用 `SUPER_ADMIN` 超级管理员、`DEPARTMENT_ADMIN` 部门管理员、`DEPARTMENT_MEMBER` 部门成员。每部门最多一个部门管理员及多个成员；每位成员只属于一个部门，权限不逐场分配。超级管理员管理所有部门、部门管理员和成员；部门管理员只能管理本部门成员及活动。成员不能管理账号、变更角色或跨部门。

其他主体包括未验证访问者、绑定活动和客户身份的 H5_CUSTOMER、现场只读大屏及 SYSTEM 任务。公开 H5/大屏仍沿用其既有入口规则，不能把成员后台权限等同于大屏访问令牌；screenToken 仍不在本次实现范围。

## 2. 后台权限矩阵

| 操作 | 超级管理员 | 部门管理员 | 部门成员 |
| --- | --- | --- | --- |
| 部门及部门管理员账号管理 | 全部部门 | 不允许 | 不允许 |
| 成员创建、编辑权限、重置密码、启停 | 全部部门 | 仅本部门 | 不允许 |
| 创建活动、修改配置及起止时间、发布、撤回、截止、结束 | 全部部门 | 仅本部门 | 不允许，即使拥有活动概览权限 |
| 归档、解除归档 | 全部部门 | 不允许 | 不允许 |
| 永久删除、删除范围预览、删除进度及失败继续 | 全部部门 | 不允许 | 不允许 |
| 归档活动查看及导出 | 全部部门，按功能读取 | 本部门，按功能读取 | 本部门且拥有对应模块权限 |
| 活动概览 | 全部部门 | 本部门 | 本部门且拥有 OVERVIEW |
| 商品管理（界面“商品导入”） | 全部部门 | 本部门 | 本部门且拥有 PRODUCT |
| 白名单管理 | 全部部门 | 本部门 | 本部门且拥有 WHITELIST |
| 现场到场 | 全部部门 | 本部门 | 本部门且拥有 ATTENDANCE |
| 订单管理（含审核、调整、恢复、作废及导出） | 全部部门 | 本部门 | 本部门且拥有 ORDER |
| 抽奖管理（界面“抽奖规则”） | 全部部门 | 本部门 | 本部门且拥有 LOTTERY |
| 完整后台审计日志 | 全部范围 | 按本部门活动范围过滤 | 不开放；可查看已授权业务模块自身的操作记录 |

勾选模块即开放与部门管理员一致的模块业务操作，不再拆分查看、导入、编辑、删除或导出子权限。业务状态与时间规则继续生效：例如商品/白名单发布锁定、活动结束后抽奖只读；订单后台维护仍可在现有允许的 ACTIVE、CLOSED、FINISHED 等状态执行，ARCHIVED 全部业务只读，删除受理后禁止后续活动访问。

所有后台请求同时校验会话、部门状态、活动归属和模块权限；修改 URL 或子资源编号不能越权。成员未授权模块在前端隐藏，后端也拒绝接口请求。导入列表按授权类型过滤，单个任务按数据库中实际 import_type 鉴权；私有源文件下载检查所属活动及模块。

订单专用客户/商品选择接口只要求 ORDER；聚合辅助接口提供客户数量、客户类型模式、到场数量及白名单发布状态，不返回客户明细。活动选择器可供成员切换本部门全部现有和新增活动；零权限成员显示“暂无功能权限”，不加载业务模块。未分类的后台接口默认拒绝成员访问。

H5 客户仍只能按会话访问本活动本人数据；只有未截止时允许首次提交或创建变更申请。公开/H5/大屏不返回完整手机号；后台白名单、到场和订单等通过相应权限校验后，按现有业务规则返回完整电话。

### 2.1 活动归档与永久删除（V051，待部署源码）

- 归档活动沿用原部门范围和功能权限，不向跨部门账号或未授权成员开放数据；仅超级管理员可归档、解除归档及管理永久删除任务。
- 活动读取保护在条件缓存和文件响应前执行；删除受理后活动列表隐藏，后续公开、H5、管理端、大屏及文件请求被拒绝，H5会话撤销，缓存身份也重新核对活动。
- 归档、删除和业务写入通过活动锁协调，保护已在途事务；归档及删除前须处理完待审批改单和未完成的导入、导出。归档时生成最终快照，之后禁止业务修改；解除归档不自动开放订货。
- 永久删除须填写原因、校验版本和活动编号；无自动备份、无回收站。清理在后台限量分批执行，持久化阶段及文件清单，重启续跑，失败自动重试并支持超级管理员手动继续；跨活动文件引用阻止物理清理。
- 删除凭证不依赖活动外键，保留活动编号、名称、部门、操作者、原因和完成情况。任务错误只返回安全提示，不向前端泄露SQL、存储键或凭证；详细错误写服务日志。

## 3. 后台认证与账号生命周期

- 统一登录页自动识别角色；姓名可中文、英文或混合，非空且最多 100 字符；用户名为 3–64 位，以英文字母或数字开头，其余允许英文字母、数字及 `_ . @ -`。
- 密码长度 8–100 位，当前使用 BCrypt（成本因子 12）哈希，不返回原密码，不记录明文密码或令牌。
- 超级管理员首次登录必须改密。部门管理员密码由超级管理员设置/重置；成员密码由所属部门管理员或超级管理员设置/重置；部门管理员和成员均不能自行改密，也不进入首次改密流程。
- 当前会话使用 HttpOnly、SameSite=Lax、Path=/ Cookie；Secure 由 COOKIE_SECURE 控制，本地默认 false。有效期由 ADMIN_SESSION_HOURS 配置，默认 12 小时；不能把设计中的空闲超时或渐进登录限制视为已实现能力。
- 写请求检查 CSRF。退出只撤销当前会话；超级管理员自行改密保留当前会话、撤销其他会话；管理员重置密码或停用账号撤销目标账号全部会话；停用部门撤销该部门全部账号会话，并继续遵守未结束活动阻止停用的现有规则。
- 权限变更提交后，后续请求读取最新授权，无需重新登录；不回滚已完成操作。前端每 15 秒、重新聚焦及收到模块权限拒绝时刷新身份并清理失效模块状态，不宣称服务端主动推送菜单变化。
- 已登录后的身份检查遇到断网、响应解析失败或服务器错误时保留当前工作区，下一次定时或聚焦检查继续重试；只有服务端明确返回 401，或成功响应确认账号、角色、部门发生变化时，才清空原登录工作区。此规则不延长服务端会话，也不放宽后端权限检查。
- 重新启用账号不恢复已撤销的旧会话，需重新登录。成员只提供停用，不删除历史审计引用。
- 共享部门管理员账号产生的旧操作仍只能归属该账号；新增成员独立登录后，业务操作归属实际成员，不能记到创建该成员的管理员名下。

## 4. H5 手机号验证安全边界

### 4.1 身份规则

```text
有类型：activityId + customerType + HMAC(normalizedPhone)
无类型：activityId + ALL + HMAC(normalizedPhone)
```

- 综合和特渠可存在相同手机号；
- 同一活动同一客户类型内重复手机号在导入阶段阻断；客户类型为空时按 `ALL` 范围唯一；
- 白名单有类型时使用客户类型 + 经销商全称 + 所属分公司判重；客户类型为空时使用经销商全称 + 所属分公司判重；
- 综合客户的大区选项来自当前生效白名单；提交具体大区时校验与白名单大区一致，提交“不分大区”时仅匹配未填写大区的客户；
- 若当前综合客户全部未填写大区，则不展示大区选择并直接进入手机号验证；
- 客户类型和大区以白名单为准，前端选择不能覆盖白名单；
- 当前白名单客户类型全部为空时不展示通道和大区选择，客户直接输入手机号；会话和商品访问仍绑定当前活动客户，不扩大到其他活动；
- 白名单客户从当前版本删除后，新验证失败；已有 H5 会话在服务端检查中失效。

### 4.2 凭证

- 凭证绑定活动客户 ID、活动 ID 和客户类型；
- 正常到期时间为活动结束时间；活动提前截止、客户从当前白名单删除或显式撤销时可更早失效；
- 默认设置 `Secure; HttpOnly; SameSite=Lax` 的不透明会话 Cookie，并限制到 H5 API 路径；不在 `localStorage`、`sessionStorage` 或 URL 保存凭证；
- H5 写请求必须携带 CSRF Token，并校验 `Origin`；Token/Cookie 不写普通日志、不由第三方统计脚本采集；
- 会话服务端绑定活动 ID、活动客户 ID、客户类型和过期时间；活动提前截止、客户从当前白名单删除或显式撤销时立即失效；
- 只有跨站 API 无法改为同站点入口时，才使用 Bearer Token，并重新配置 CORS、凭证存储和撤销策略。

### 4.3 频率限制

业务要求是不因连续失败阻止正常客户，因此限流采用宽松的技术保护而非永久锁定：

- 单手机号 HMAC：20 次/分钟；
- 单 IP：300 次/分钟，考虑活动现场共享 NAT；
- 单活动全局：按压测容量设置令牌桶；
- 超限仅短期返回 429，不把白名单身份永久锁定；
- 验证失败率异常上涨触发告警。

这些值是配置默认值，应在压测后调整。

## 5. 数据保护

- 全站 HTTPS，正式环境启用 HSTS；
- 手机号在白名单、到场和订单业务表中按要求保存为明文，并保留 HMAC 查询索引；仅白名单、现场到场和订单管理向通过部门与模块授权的后台账号显示完整号码，其余页面和接口脱敏或不返回；导入预览敏感载荷仍使用应用层加密；
- 加密密钥不写数据库、不提交 Git，由环境密钥管理提供；
- 日志过滤 `phone`、`token`、`password`、Cookie 和 Authorization；
- H5 和大屏不显示完整手机号；后台订单列表按 ORDER 或管理员权限返回现有业务所需号码；
- 白名单/到场管理接口必须鉴权和授权；导出、编辑、删除等变更操作写审计，生产环境可进一步增加明文查看审计；
- 测试环境使用虚构手机号，不复制正式数据；
- 数据库账号按最小权限配置，应用账号不具备建库和管理员权限；Flyway 使用独立迁移账号。

### 5.1 数据库迁移部署

当前本地 Docker Compose 环境由 Spring Boot 启动时执行 Flyway。以下是正式生产发布约束：

- 正式环境由发布流水线启动一次性 Migration Job 执行 Flyway；不在 API 或 Worker 启动钩子中执行 `migrate`；
- Migration Job 使用独立迁移账号，API/Worker 运行账号不授予 DDL 权限；Flyway 的数据库锁只作为额外保护，不能替代独立部署职责；
- 迁移成功后才发布 API 和 Worker。迁移失败停止发布；涉及滚动发布的字段变化必须先采用向前兼容的 expand/contract 方案；
- 已执行的迁移文件不可修改，只能追加新版本，并在预发布环境完成备份恢复和兼容性验证。

## 6. 输入、浏览器和文件安全

- JSON 请求大小、字段长度、数组行数在网关和应用层双重限制；
- 富文本说明默认按纯文本处理；如允许 HTML，必须使用白名单净化；
- 配置 CSP、`X-Content-Type-Options: nosniff`、Referrer-Policy 和 frame-ancestors；
- CORS 仅允许配置的 H5、后台和大屏域名；
- 对象存储默认私有，商品图片通过受控公开域名或签名 URL；
- 上传校验文件扩展名、MIME、魔数、大小和 SHA-256；
- 白名单/到场名单导入预览中的手机号原始值使用加密载荷保存，普通 JSON 和错误表只保存脱敏值；
- ZIP 限制解压后文件总数、总大小和压缩比，防止 ZIP Bomb；
- ZIP 文件名标准化并禁止 `../` 路径穿越；
- Excel 解析限制 Sheet、行列数量，单元格公式不在服务器执行；
- 导出 CSV/Excel 时对以 `= + - @` 开头的文本做公式注入转义。

## 7. 订单并发控制

### 7.1 同一客户首次同时提交

- `customer_order(activity_id, activity_customer_id)` 唯一约束保证只创建一个订单；
- 第一个事务成功后，第二个事务读取已存在订单；
- 如果幂等键相同且载荷相同，确认原提交已完成并返回该订单的最新状态，不重新执行写入；
- 如果幂等键不同，第二个请求按 `expectedVersion=0` 返回版本冲突，不自动覆盖。

### 7.2 两个页面同时修改

更新条件：

```sql
UPDATE customer_order
SET lock_version = lock_version + 1, current_version_no = current_version_no + 1, ...
WHERE id = ? AND lock_version = ? AND current_version_no = ?;
```

影响行数为 0 即返回 `ORDER_VERSION_CONFLICT`。订单主表、当前明细、版本和版本明细位于同一事务。

### 7.3 客户截止瞬间提交

- H5 事务开始后再次读取数据库可信时间和活动状态；
- H5 请求在 `now >= ends_at` 时立即拒绝，即使页面按钮仍显示可提交；
- 自动截止任务延迟不影响判断，因为 H5 写接口同时校验 `ends_at`；
- 已在截止前完成事务提交的 H5 订单有效，截止后才提交事务的 H5 请求拒绝；管理员订单写请求按角色和活动状态校验，可在 `CLOSED`、`FINISHED` 继续维护。

### 7.4 商品价格自动同步

- 商品保存和当前活动有效订单价格更新先锁定同一活动行，保证商品最新规则与订单计价读取顺序一致；
- 只处理同活动、同商品 ID、状态为 `SUBMITTED` 的订单；撤回、作废和其他活动订单不处理；
- 更新 `order_item` 当前价格、小计和 `customer_order.total_amount`，不修改数量、吨数、当前版本号，不新增 `order_version` 或 `order_operation`；
- 更新事务提交后写 `ORDER_PRICE_UPDATED` outbox，缓存失效和 SSE 只在提交成功后发生；失败时商品和订单一起回滚。

## 8. 幂等实现

### 8.1 请求指纹

对规范化后的请求体计算 SHA-256，连同调用者、活动、接口代码和 `Idempotency-Key` 保存。

处理流程：

1. 尝试插入 `PROCESSING` 幂等记录；
2. 唯一键冲突时读取现有记录；
3. 请求哈希不同：409 `IDEMPOTENCY_KEY_REUSED`；
4. 状态 `COMPLETED`：返回保存的 HTTP 状态和响应摘要；
5. 状态 `PROCESSING`：短暂等待或返回处理中；
6. 主业务与幂等完成状态必须在同一 MySQL 事务提交；异步任务至少要把任务记录、幂等记录和业务唯一键绑定在 MySQL 中；
7. 超时扫描器依据业务唯一键恢复卡住记录。

H5 `ORDER_SUBMIT` 的确认规则（2026-10-30 用户确认）：已完成请求的重试返回后台最新订单，包括后续管理员调整，不固定返回首次响应。新版精简回执和升级前带 `resultJson` 的 format-2 回执均按保存的订单 ID 重新读取；请求指纹、活动/客户身份、完成状态校验仍先执行。`includeHistory` 按已校验的请求参数处理，旧回执不需要补字段或重写。重试不得新建订单、增加订单版本、覆盖管理员修改或清除后续草稿。更早的不完整记录仍返回 `IDEMPOTENCY_RESULT_UNAVAILABLE`，提示加载最新订单，绝不重新执行写入。其他接口的幂等规则不因此改变。

不能只把幂等结果放 Redis。Redis 只能作为快速命中缓存或互斥加速，Redis 丢失、过期或重启后必须回到 MySQL，不能因此重复产生订单版本、导入发布或抽奖结果。

## 9. 导入并发和事务

- 同一活动、同一数据类型只允许一个有效的未确认预览；重新上传在活动行锁保护下取消此前可替换的预览任务；
- 同一导入任务的预览行编辑和删除必须先锁定 `import_task` 行并串行执行，避免多个事务同时重新校验同一任务造成锁顺序冲突或死锁；
- 预览编辑客户端必须等待 staging 事务提交和重新校验成功后才关闭抽屉；请求失败时保留输入。缺少任务 ID 或 staging 行 ID 时禁止本地兜底保存，避免页面显示与数据库实际发布内容不一致；
- 商品、白名单和现场到场的预览批量删除使用一个集合请求和一个数据库事务：按 ID 稳定顺序锁定所选 staging 行，统一标记删除后只调用一次任务重新校验；任一步失败时整批回滚；
- 前端不得通过 `Promise.all` 等方式并发发送同一导入任务的多个单行删除请求；正式数据尚无批量接口时应串行调用，避免部分失败和并发写入风险；
- 确认时对活动记录或“活动 + 数据类型”互斥资源加锁；
- 任务进入 `CONFIRMING` 状态后预览行不可编辑；
- 商品确认请求中的图片决定必须校验 ZIP 相对路径唯一、状态白名单和目标 staging 行归属；`CONFIRMED` 目标必须为同一标准化商品名称，一个名称最多一张正式图、一张正式图最多一个名称；`PENDING` 可覆盖多个同名候选行并随发布版本固化。决定与辅助 ZIP 一并固化到 `import_task`，Worker 只能执行已固化决定；
- 商品图片预览关系以“完整标准化商品名称 + ZIP 路径”归组，物料代码不参与匹配；商品名称中的 `/` 不得按文件路径取 basename，只有 ZIP 归档路径按路径规则处理。单条商品保存只能同步同名商品，不得遍历修改其他名称关系。旧客户端关系缺少状态时按候选处理，禁止以 `status != PENDING` 之类的宽松条件静默确认；
- 发布后选择候选须在事务内锁定当前版本的待确认记录，同时排除同名称其他候选和同文件在其他名称下的候选，再替换同名称全部商品行的正式单图；重复提交或版本已切换时返回 404/409，不得把旧候选写入新版本；
- 确认前记录当前基础数据版本，版本变化时返回冲突并要求重新预览；
- 现场到场试算响应携带当前白名单 `import_publish_version.id`。确认请求必须回传该 ID，并固化到 `import_task.match_base_version_id`；确认事务与 Worker 发布事务均比较当前白名单版本，不一致时返回/记录 `ATTENDANCE_WHITELIST_VERSION_CHANGED`，不得用旧试算结果继续发布；
- staging 解析和编辑不修改当前目录；当前由应用内任务执行器完成发布，生产拆分 Worker 后承接同一职责；
- 最终发布只在短事务内切换活动 + 数据类型的当前版本指针，失败不改变当前目录；
- 商品与白名单分别锁定，互不影响；
- 发布活动与商品/白名单导入确认竞争时，以活动版本和当前正式绑定之后的新未完成任务校验保证只有一个先成功；已被正式版本覆盖的历史预览不得阻断发布；进入 `SCHEDULED` 后不再接受商品或白名单导入确认。

当前本地任务由应用内执行器运行并以 MySQL 状态为准。生产拆分 DB Task Queue 后，任务领取使用租约和状态条件更新；租约过期后允许重新领取，处理器必须依据 MySQL 当前状态、任务幂等键和业务唯一约束避免重复副作用。Redis 不作为任务队列的唯一来源。

## 10. 抽奖并发和随机性

- 当前Redis辅助锁键为`order-show:lottery:round:{roundId}`，TTL为30秒；Redis不可用时数据库行锁继续保证单轮执行；
- 数据库使用`SELECT ... FOR UPDATE`锁定轮次并校验READY/RESET及前序完成状态，快照/中奖/轮次更新保持同一事务；
- `lottery_draw_attempt(round_id, attempt_no)`、每次尝试内候选/中奖人/位置唯一约束是第三道防线；
- 安全随机源使用 Java `SecureRandom`；
- 候选生成前按当前有效数据重新校验，并固定规则与候选快照；
- 规则JSON保存客户与商品条件、门槛、概率模式和权重单位/总权重；SHA-256结果摘要v2包含轮次/尝试、概率模式、候选ID及三项小计、随机键和中奖ID，用于结合快照事后核验；
- 任何实例崩溃后以 MySQL 事务状态为准，Redis 锁过期不能改变已保存结果；
- 结果提交成功前不向大屏发送中奖名单。

抽奖与H5共用数据库资源，需要单独限制昂贵查询：

- 每后端实例试算和商品选项共用`LOTTERY_PREVIEW_CONCURRENCY=2`个名额，开奖使用独立`LOTTERY_DRAW_CONCURRENCY=1`个名额；进入事务前尝试取得，超额立即503 `LOTTERY_BUSY`，`Retry-After: 2`，不排队占用数据库连接；
- `LOTTERY_QUERY_TIMEOUT_SECONDS=8`限制候选及商品选项的单条查询，不代表完整开奖事务超时，不修改共用连接池或H5写入名额；
- 后端和Compose内置相同默认值，`.env.example`说明覆盖入口；实际`.env`可省略。多个后端实例分别计算名额，部署时按共享数据库容量核定总量；
- 只手动试算当前轮、一次汇总匹配小计；开奖候选每批250、中奖批量写入，失败全部回滚；
- 具体默认值的本机混合测试及局限见[三种加权验证](../testing/lottery-weighting-2026-10-31.md)，不能由单次短时测试承诺线上无资源影响。

## 11. 缓存和 SSE 一致性

- 订单事务写入 outbox 事件；
- outbox 发布器提交后删除/刷新活动看板缓存并向各 API 实例广播；
- SSE 推送 `dashboard.invalidated`，客户端重新获取快照；
- 看板响应包含 `version` 和 `generatedAt`；
- 缓存失效失败由 outbox 重试；客户端还有低频轮询兜底；
- Redis 丢失后从 MySQL 重建，不影响订单和中奖事实。

## 12. 必须审计的操作

| 操作码 | 内容 |
| --- | --- |
| `ADMIN_LOGIN` | 登录成功或失败，不记录密码 |
| `ADMIN_PASSWORD_CHANGED` | 修改密码和会话撤销 |
| `ACTIVITY_CREATED/UPDATED` | 活动配置前后值 |
| `ACTIVITY_STATUS_CHANGED` | 状态、原因和时间 |
| `ACTIVITY_ARCHIVE/ACTIVITY_UNARCHIVE` | 归档或解除归档的活动、操作者和原因 |
| `ACTIVITY_DELETE_REQUESTED/ACTIVITY_DELETE_RETRY` | 删除受理或失败继续；审计不再挂靠将被删除的活动，进度与完成情况由独立任务保留 |
| `IMPORT_UPLOADED/CONFIRMED/FAILED` | 文件摘要、统计和错误 |
| `PRODUCT_UPDATED/DEACTIVATED` | 单条紧急变更前后值和原因；价格变更的相关当前订单金额由同一商品变更事务更新，不另写订单操作 |
| `CUSTOMER_UPDATED/DEACTIVATED` | 白名单变更前后值和原因 |
| `ORDER_WITHDRAWN` | 订单变更申请审核通过后撤回订单的订单号、原状态和操作时间 |
| `H5_CHANGE_REQUESTED/APPROVED/REJECTED` | 客户变更申请快照、审核结果、管理员和原因 |
| `EXPORT_CREATED/DOWNLOADED` | 导出类型、筛选和文件，不记录下载内容 |
| `LOTTERY_RULE_PUBLISHED` | 规则快照 |
| `LOTTERY_DRAWN` | 轮次、候选数、结果哈希 |
| `LOTTERY_COMPLETED` | 现场完成时间 |
| `LOTTERY_RESET` | 原结果、原因和管理员 |
| `ADMIN_USER_CREATED/UPDATED` | 管理员账号生命周期（含重置密码、启停） |

V035 起，订单操作、订单版本、订单审核和审计日志保存实际账号 ID 及相应操作时身份快照；订单操作和审计还保存角色快照。前端展示具体姓名与用户名，成员改名或停用不改变新记录；旧共享账号记录不补造个人信息。成员管理审计包含目标账号、权限、状态及是否重置密码，不记录密码。

审计日志只追加，普通业务接口无删除能力。超级管理员明确永久删除整场活动时，该活动的审计随清理任务删除；删除受理、重试审计和独立任务凭证不挂靠被删除活动，继续保留。`before_json`、`after_json` 中手机号仅保存脱敏值或 HMAC 摘要。

## 13. 日志与追踪

- 入口生成 `trace_id`，贯穿 API、SQL 慢查询标签、审计和 outbox；
- 应用日志使用结构化 JSON；
- 订单和抽奖成功日志只记录 ID、状态、耗时和版本；
- 4xx 业务错误按指标统计但不打印堆栈；
- 5xx 记录堆栈并告警，响应只返回 trace ID；
- 监控验证成功率、提交成功率、版本冲突率、导入失败率、SSE 在线数、outbox 积压和抽奖失败。

## 14. 备份与恢复默认目标

在正式部署方案未确定前采用以下设计目标：

- 数据库 RPO 不超过 5 分钟；
- 核心业务 RTO 不超过 60 分钟；
- 每日全量备份 + binlog/增量恢复；
- 对象存储开启版本保护或至少每日备份；
- 加密密钥单独备份，且访问受控；
- 每场正式活动前执行一次恢复演练；
- 活动现场保留最近看板只读快照，但不得在后端故障时离线接受新订单。

这是架构验收默认值，正式采购基础设施前可依据成本和公司制度调整。

## 15. 上线安全与并发验收

- 2000 人真实行为模型压测，而不是只压一个健康检查接口；
- 重复点击、网络重试不会增加订单版本；
- 两个设备同时修改只成功一个；
- 截止瞬间无法绕过服务端时间；
- 同一轮 20 个并发抽奖命令只产生一份结果；
- Redis 清空后订单、抽奖和看板可以从 MySQL 恢复；
- 导入确认中断不产生半批数据；
- 非当前活动令牌无法跨活动访问；
- 日志、错误响应和大屏中没有手机号、密码或 Token；
- 数据库和对象存储备份恢复达到 RPO/RTO 目标。
