# 订购会系统数据库设计

## 1. 设计原则

V040/V041 订单级看板汇总：新增 `order_dashboard_stat`（每单一行）及 `order_dashboard_product_line_stat`（每单按项目组、礼盒标志聚合）。V041 删除 V040 的三个逐明细触发器；开启汇总时由应用在业务事务中同步标脏/重算，关闭时不维护。汇总是可重建的派生数据，不替代订单、历史版本或冻结展示快照。裸 SQL 修改明细或关闭期间写入后，需显式修复和对账再恢复汇总读取。2026-10-30 本地已升级至 V041 并开启，其他环境需独立升级和回填，见[部署记录](../deployment/2026-10-30-summary-local.md)。

V035 部门成员：取消 `admin_user.department_id` 的全账号唯一约束，改用生成列 `department_admin_scope` 的唯一索引，仅限制每部门一个部门管理员；新增成员角色、模块权限表及操作身份快照。保留已有账号、活动与订单 ID。

V034 审核工作台：`order_change_request` 状态限制为 PENDING/APPROVED/REJECTED；历史 CONFLICTED 转为 REJECTED。生成列 `pending_order_id` 和唯一索引保证每张订单最多一条待审核申请。`original_order_json` 保存申请时原订单快照用于准确对比；迁移前申请使用对应历史版本兜底，不伪造旧价格快照。替换申请和自动驳回保留申请历史及 SYSTEM 操作记录。

- MySQL 是订单、抽奖和审计的唯一事实来源；
- 所有活动业务表显式包含或可通过父记录唯一追溯到 `activity_id`；
- 多场活动数据永久保留，新导入不得覆盖历史活动；
- 当前订单数据与历史版本快照分离；商品属性、删除和版本切换不改变历史版本，商品价格保存时按规则更新当前活动有效订单的当前金额；
- 金额使用定点小数，禁止使用 FLOAT/DOUBLE；
- 业务页面删除当前版本数据；数据库内部可使用可见标记或删除时间保护历史引用，订单版本、中奖结果和审计日志不可物理删除；
- 数据库唯一约束是并发一致性的最后防线，不能只依赖 Redis；
- 时间字段使用 `DATETIME(3)` 保存 UTC 时间点，展示时按活动时区转换。

## 2. 标识策略

- 内部主键：`BIGINT UNSIGNED AUTO_INCREMENT`；
- 活动公开标识：不可变且唯一的 `activity_code`，用于二维码和 URL；
- 订单公开标识：唯一 `order_no`，首次提交生成，版本变化时不改变；
  新订单号采用`ZY`加完整UUID的Base36编码（最长27字符），不再截取4位随机字符；既有订单号不重写，唯一约束继续保留。
- 导入、导出、抽奖等资源对外 API 不直接暴露可枚举信息时，可在应用层增加 ULID；第一期后台鉴权资源允许使用数字 ID。

## 3. 手机号保护

按业务要求，最终白名单、到场和后台订单查询使用标准化手机号明文；接口层仍按访问场景控制是否返回完整号码：

| 字段 | 用途 |
| --- | --- |
| `phone` / `confirmer_phone` | 标准化后的经销商手机号、确认人手机号；仅通过部门及模块授权的后台白名单、到场和订单接口可返回完整值 |
| `phone_lookup_hash` | `HMAC-SHA-256(environment_secret, normalized_phone)`，用于精确匹配；唯一约束另组合活动、数据版本和客户类型 |
| `phone_masked` | H5、公开页面、排行、战报、抽奖大屏和日志等非明文场景展示，例如 `138****1234` |
| `phone_ciphertext` / `confirmer_phone_ciphertext` | V023 迁移兼容列；应用启动时迁移旧数据后清空；迁移窗口内仅允许后台查询做旧密文只读兜底，不用于新写入 |
| `phone_key_version` | 旧加密数据迁移兼容字段，保留用于历史结构兼容 |

后台客户手机号搜索直接按标准化明文字段精确匹配，也保留 HMAC 索引作为身份校验和唯一约束；迁移窗口内若历史记录仍只有旧密文，后台查询会对当前活动白名单范围做只读解密兜底。订单管理支持规范化手机号和脱敏手机号后四位匹配。已登录后台账号访问白名单、现场到场和订单管理接口时，后端按部门范围及相应模块权限返回完整 `phone`；白名单同时可返回完整 `confirmerPhone`。这些字段不得进入公开/H5/大屏接口、缓存、普通日志或审计载荷。

## 4. 数据域与表

### 4.1 后台账号与权限

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `department` | 业务部门 | 编码唯一且不可修改；部门停用使所属账号不可继续访问 |
| `admin_user` | 超级管理员、部门管理员和独立成员 | 用户名全局唯一；角色为 SUPER_ADMIN / DEPARTMENT_ADMIN / DEPARTMENT_MEMBER；超级管理员不绑定部门，另两类必须绑定一个部门 |
| `admin_user_permission` | 成员的六项模块权限 | 主键为账号 ID + permission_code；权限值仅 OVERVIEW、PRODUCT、WHITELIST、ATTENDANCE、ORDER、LOTTERY |
| `admin_session` | 所有后台账号登录会话 | 只保存令牌哈希；支持按账号撤销 |

V035 将原 `uk_admin_user_department` 改为普通部门索引，并增加生成列 `department_admin_scope`：仅 DEPARTMENT_ADMIN 取 department_id，其他角色取 NULL；`uk_department_admin_scope` 保证一个部门最多一个部门管理员，包括停用的管理员账号。多个成员可属于同一部门。用户名约束仍全局生效。

部门管理员显示名跟随部门名称，成员显示名独立保存，允许中文、英文或混合，去除首尾空白后不能为空且最多 100 字符。登录用户名为 3–64 位，以英文字母或数字开头，其余允许英文字母、数字及 `_ . @ -`；姓名与登录用户名是不同字段。

成员权限覆盖部门全部活动，不新增活动与成员授权表。没有权限行的成员没有业务模块权限；管理员按角色拥有其数据范围内的全部模块权限。成员编辑使用 lock_version 防止覆盖其他管理员的并发修改；权限集合整体替换与成员更新在同一事务完成。

密码只保存 BCrypt 哈希，长度 8–100 位；部门管理员密码由超级管理员管理，成员密码由所属部门管理员或超级管理员管理，两类账号均不自助改密。停用账号、重置密码和停用部门撤销已有会话；账号停用不物理删除历史引用。

### 4.2 活动

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `activity` | 活动名称、编号、订货时间、整场活动时间、状态和展示配置 | 活动编号唯一；开始时间早于订货截止时间，订货截止时间不晚于整场活动结束时间 |

正常活动状态为：`DRAFT`、`SCHEDULED`、`ACTIVE`、`CLOSED`、`FINISHED`。`CLOSED` 只表示订货截止，H5 订单和基础数据变为只读，但现场抽奖及实时看板仍可继续；到达 `event_ends_at` 或管理员立即结束后进入 `FINISHED`，停止抽奖写操作和 SSE 实时推送。数据库中的 `ARCHIVED` 保留为历史兼容状态，当前界面和正常流程不提供活动归档操作。草稿活动可以时间重叠；同部门占用发布时间的已发布活动，完整时间段（开始至整场结束）不得重叠，订货已截止但整场未结束也占用该时段；不同部门可并行。正式 H5 入口按活动编号定位，不依赖全局唯一活动。

### 4.3 文件、导入和导出

| 表 | 作用 |
| --- | --- |
| `stored_file` | 对象存储文件元数据 |
| `import_task` | Excel/ZIP 导入批次、统计及图片人工匹配决定 |
| `import_staging_row` | 解析预览、校验状态、人工编辑结果 |
| `import_publish_version` | 已校验、可发布的不可变数据集版本、摘要和来源任务 |
| `activity_data_binding` | 活动 + 数据类型当前生效版本指针 |
| `import_error` | 定位到 Sheet、行、字段的错误 |
| `export_task` | 后台异步导出任务 |

Excel 解析、标准化、校验和人工编辑只写入 staging，不修改当前商品/白名单。商品和白名单每次均按独立完整批次预览，不计算跨版本新增、更新、未变化或移除。确认后由当前 Spring Boot 应用内任务执行器将 staging 物化为不可变的 `import_publish_version` 及其版本化商品/客户行；生产环境拆分独立 Worker 后承接同一职责。最终发布事务只锁定活动 + 数据类型，校验基础数据版本和任务状态，并切换 `activity_data_binding` 的当前版本指针，同时写审计和 outbox。读请求只能读取当前指针对应的版本，因此不会看到半批数据。

版本化商品/客户行可以使用独立版本表，也可以在现有领域表增加 `data_version_id`；物理实现不同不影响契约：所有当前查询必须先解析当前指针，再限定到同一个发布版本，不能混读旧版本和新版本。

旧版本在保留期内不删除，可用于审计和回滚；历史版本读取提交时快照，当前订单读取 `order_item` 当前明细。商品属性、商品删除和商品版本切换不影响历史版本；基础箱价或阶梯规则保存时，当前活动的 `SUBMITTED` 订单按商品 ID 自动更新当前价格、小计和总金额，不回写 `order_version_item`，不新增 `order_operation`。`import_task` 和 `export_task` 同时承担 DB Task Queue 记录，必须保存状态、租约、尝试次数、下次重试时间和最后错误摘要。现场到场任务确认时把实时试算所依据的白名单发布版本保存到 `import_task.match_base_version_id`，确认入口和 Worker 发布前均校验该版本仍为当前白名单，防止预览与发布之间发生基础数据漂移。

白名单和到场名单的预览行可能包含手机号。此类原始/编辑载荷写入 `sensitive_data_ciphertext`，普通 JSON 只保留脱敏预览；`import_error.raw_value_masked` 同样不得保存手机号明文。导入任务完成并超过排障保留期后，可以清理预览密文，但原始文件仍按受控对象存储策略保留。

### 4.4 客户和商品

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `customer` | 跨活动永久经销商身份 | 客户类型 + 标准化全称 + 标准化所属分公司唯一；客户类型可为 `ALL` |
| `activity_customer` | 当前活动白名单和资料快照 | 活动 + 客户类型 + 标准化全称 + 标准化所属分公司唯一；手机号按客户类型 HMAC 唯一，明文仅供受控后台使用 |
| `activity_attendee` | 当前活动到场人员及本版本白名单关联结果 | `data_version_id` 限定当前全量版本；`match_status` 为已关联、待确认或未关联 |
| `activity_product` | 当前活动商品目录 | 活动 + 业务键唯一；分别保存是否展示和是否可订 |
| `activity_product_branch_scope` | 分公司定制品允许范围 | 商品 + 标准化分公司唯一 |
| `product_image` | 商品图片历史及当前单图 | 商品 + 文件唯一；新写入规则保证每个标准化商品名称当前最多一张图，旧多图仅作历史兼容 |
| `product_image_review_candidate` | 已发布商品版本尚待人工处理的 ZIP 图片候选 | 版本 + 文件 + 标准化商品名称唯一；状态为待确认、已选择或已排除 |

`activity_product` 唯一约束按活动 ID、数据版本 ID 和应用层计算的 `business_key` 生效；`business_key` 由客户类型、返利类型、标准化物料名称和标准化物料代码组成。判重先按客户类型 + 返利类型 + 标准化名称分组；代码都非空时，名称与代码相同才重复，代码不同允许；任一代码为空时，同名即重复。发布预校验和手动维护校验负责执行“空码与有码同名”规则，数据库唯一键同时保护名称与代码都相同的商品。物料代码仍可为空，图片匹配仍只按名称进行。

商品批量导入使用一个非空 Sheet，Sheet 名称不参与业务判断；客户类型只允许 `综合`、`特渠` 或空，是否返利只允许 `是`、`否` 或空，物料名称必填，物料代码和产品说明可为空。产品说明写入 `activity_product.description`，由商品目录接口返回给 H5 商品详情；H5 根据当前目录是否同时存在两种明确返利状态决定显示“全部商品”或“返利产品/非返利产品”页签，空返利商品作为通用商品处理。

每次商品 Excel 与确认时附带的图片 ZIP 形成独立版本。新版本不复制上一版本的 `product_image` 关联，也不继承 `ZIP_IMPORT` 或 `MANUAL` 图片；旧图片关联保留在旧版本供历史订单与审计读取。图片 ZIP 写入 `import_task.auxiliary_file_id`，预览关系写入 `import_task.image_decisions_json`。`CONFIRMED` 关系写入 `product_image`，`PENDING` 关系连同候选文件写入 `product_image_review_candidate`；二者都必须在切换当前版本前完成。待确认候选不属于正式商品图，因此商品可以先发布，H5 继续显示占位图，管理员再从当前版本逐个选择或排除。旧版本候选随版本绑定失效但继续保留供审计。

图片 ZIP 以单张图片为匹配单位。匹配前先校验品种、容量、装箱数、容器材质、瓶型和外包装，明确冲突不自动关联；ZIP 相对路径只用于恢复图片文件名，不能把 Excel 商品名称中的 `/` 当作路径并截断品牌或品种。图片只按标准化物料名称试算和确认，物料代码不参与图片匹配：同一名称只能选一张图，名称相同的商品行共享结果，不同名称不能共用同一张最终图片。匹配到多图或无法唯一判断时商品为“待确认”，选择一张后为“已匹配”并自动排除同名称的其他候选及该文件在其他名称下的候选，全部排除后为“未匹配”。手工上传替换图时也会排除该名称剩余候选；后台预览列表对“待确认”商品显示其候选图片数量数字。

商品展示与可订分离：已启用且物料名称有效时 `is_visible=true`；仅当元/箱存在且大于 0 时 `is_orderable=true`。物料代码、元/瓶、规格、箱规和吨箱转换系数均可空，不影响展示；吨箱转换系数为空不影响下单。

### 4.5 订单

V035 新增身份快照：`order_operation.actor_identity_snapshot` 和 `actor_role_snapshot` 保存操作时姓名、用户名及角色；`order_version.actor_identity_snapshot` 保存提交账号身份；`order_change_request.reviewer_identity_snapshot` 保存审核人身份。`audit_log` 也保存身份与角色快照。实际账号 ID 仍为归属依据；旧记录不伪造快照，空快照沿用原账号查询展示。

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `customer_order` | 每个活动客户的唯一当前订单 | 活动 + 活动客户唯一；订单号唯一 |
| `order_item` | 当前订单明细、当前成交价和商品属性快照 | 订单 + 商品唯一；价格变化可自动更新当前明细 |
| `order_version` | 每次成功非空提交的不可变版本 | 订单 + 版本号唯一 |
| `order_version_item` | 提交版本的商品和客户/商品价格快照 | 版本 + 行号唯一；调价前补存尚未冻结的提交快照，已有快照不回写 |
| `order_operation` | 客户提交、变更申请、审核及后台新增、调整、恢复、作废等操作记录 | 只追加；商品自动调价不新增 |
| `order_change_request` | 有效订单的减量/删除商品/撤回申请及审核结果 | 订单同一时间最多一条 `PENDING`；申请快照不直接计入业务统计 |
| `api_idempotency` | 命令请求的持久幂等记录 | 活动 + 调用者 + 接口 + 幂等键唯一 |
| `price_sync_batch` | 历史价格补处理兼容表 | 当前自动计价不写入；保留已执行批次结构 |
| `h5_order_draft` | H5 未提交购物车草稿 | 活动 + 活动客户唯一；外键同时约束活动和活动客户 |

`api_idempotency` 保存规范化请求指纹、`PROCESSING/COMPLETED/FAILED` 状态、任务 ID 和可重放的响应摘要。关键业务变更与幂等完成状态必须在同一 MySQL 事务内提交；Redis 只缓存已知结果或做快速互斥，不能替代该记录。

`h5_order_draft` 只保存商品 ID 与数量 JSON、草稿所基于的 `base_order_version`、草稿锁版本、更新时间和过期时间，不保存手机号、客户名称、价格或订单金额。保存、读取和删除必须同时满足 H5 会话中的 `activityId` 与 `activityCustomerId`；请求体中的客户 ID 仅作一致性校验，不能改变会话身份。草稿商品每次保存都重新校验当前商品版本、客户类型、分公司范围、可见和可订状态。

草稿不属于正式订单事实：首次提交前可以存在 `h5_order_draft`，但不存在 `customer_order`、订单号和订单版本。草稿 `base_order_version` 必须等于客户当前订单版本，防止旧页面覆盖已经提交或修改的订单；首次提交、纯增量更新、失效订单恢复或创建变更申请成功时删除草稿，审核申请不会再从草稿恢复。H5 直接提交或变更申请的成功幂等重放只返回原响应，不删除后来保存的新草稿。`expires_at` 不晚于活动截止时间，过期草稿不再恢复。

H5 ORDER_SUBMIT 的 response_json 使用 format=2，保存 orderId、orderVersion、resultJson（订单响应 JSON 字符串，保留十进制精度）；沿用现有唯一约束，无结构迁移。expires_at 至少覆盖活动结束后 30 天，清理还检查 completed_at 及当前活动结束时间，每小时最多 500 条，仅处理新格式已完成的 H5 提交。详见 [幂等重试与清理](../testing/h5-idempotency-retry.md)。

 V010 新增草稿表；V011 将早期受 MySQL `Asia/Shanghai` 会话默认值影响的明显未来时间校正为 UTC；V020 统一商品导入字段并增加产品说明；V021 增加白名单所属分公司身份键和不区分客户类型 `ALL`；V022 增加管理员订单创建、调整、作废所需的来源、管理员、原因和版本操作字段；V023 增加手机号明文业务列并配合应用启动迁移旧密文；V032 增加抽奖轮次概率模式，历史轮次默认为等概率；V033 增加订单变更申请及审核快照。后续草稿写入显式使用 `UTC_TIMESTAMP(3)`，API 返回 ISO 8601 UTC，页面按 `Asia/Shanghai` 展示。

业务状态只有：

- `SUBMITTED`：参加统计和抽奖；加权使用当前有效订单中匹配商品的金额、箱数或吨数小计，无商品筛选的金额/箱数可复用订单合计；
- `WITHDRAWN`：保留最近一次非空明细，但不参加统计和抽奖；
- `VOIDED`：管理员逻辑作废，保留订单号、明细、版本和操作记录，不参加统计和抽奖。

活动 `CLOSED` 或 `FINISHED` 后客户侧订单只读，不批量改写订单状态；超级管理员、本部门管理员及拥有 ORDER 权限的本部门成员仍可新增、调整和逻辑作废。订单变化会按最新有效订单更新看板、排行和战报，订单版本及操作记录持续保留。历史数据库中若存在 `ARCHIVED` 状态，沿用兼容读取规则，但不作为当前业务入口。

### 4.6 访问、看板和抽奖

| 表 | 作用 |
| --- | --- |
| `visit_event` | H5 打开、验证成功/失败、查看商品和提交结果事件 |
| `lottery_rule` | 活动抽奖规则组 |
| `lottery_round` | 每一轮配置和执行状态 |
| `lottery_draw_attempt` | 每次实际抽取的不可变规则快照、结果哈希和有效状态 |
| `lottery_candidate_snapshot` | 开始抽奖时固定的经销商候选快照 |
| `lottery_winner` | 永久中奖结果及有效/作废标记 |
| `activity_dashboard_snapshot` | 整场活动结束时生成、管理员订单维护后可更新的排行与战报 JSON 快照 |
| `domain_event_outbox` | 事务提交后可靠触发缓存失效和 SSE 通知 |

活动结束前，看板数据可以缓存在 Redis，缓存丢失时从 `customer_order` 和 `order_item` 重建。活动进入 `FINISHED` 时生成最终排行和战报快照；管理员后续新增、调整或作废订单时自动刷新该快照，无需运营人员手工重新生成。`FINISHED` 页面不再接收 SSE，但刷新页面可读取最新快照。数据库中若存在历史 `ARCHIVED` 状态，则继续读取其已有快照，不作为当前正常流程。

抽奖候选的业务主体始终是 `activity_customer`。当候选范围为 `ATTENDEES` 时，只选取当前到场发布版本中 `match_status=MATCHED`、且仍指向当前有效白名单版本的活动客户，并按 `activity_customer.id` 去重；`PENDING_CONFIRMATION` 和 `UNMATCHED` 不进入候选池。

`activity_attendee.match_method` 新关联仅记录名称精确关联依据：`FULL_NAME_BRANCH`（客户类型 + 分公司 + 经销商全称）、`FULL_NAME`（无分公司范围时的历史/兼容全称匹配）、`SHORT_NAME` 或 `MANUAL`；`PHONE` 仅为兼容历史记录保留，新计算不再产生。现场手机号只作联系信息，不参与客户身份关联。Excel 发布不更新上一版本行，而是创建新版本并重新计算全部关联。白名单版本切换后，当前到场版本也必须在同一发布事务中重新计算，不能保留旧白名单关联。

抽奖不创建实体奖券。`lottery_round.probability_mode` 支持 `EQUAL`、`ORDER_AMOUNT_WEIGHTED`、`ORDER_BOX_COUNT_WEIGHTED`、`ORDER_TONS_WEIGHTED`。加权模式使用有效SUBMITTED订单匹配商品的实际金额/箱数/吨数，先按最低门槛排除，再对剩余候选求总权重；对应权重0或缺失时排除，最低门槛0不取消该要求。吨数缺失部分按0计，有部分已知时按实际合计参与。

V045新增最低吨数、项目组、品种数组和未填写筛选标记，候选快照增加吨数和缺失换算明细数；项目组与品种必须命中同一条明细。V046扩展概率模式约束并约束新增箱数/吨数模式与门槛一致。V032原有等概率默认值和历史金额组合保留，不重算已开奖数据。V045/V046在本轮仅应用于隔离测试库，未迁移业务库。

开奖规则JSON保存概率模式、`weightMetric`、`totalCandidateWeight`和三种门槛/商品条件；`totalCandidateOrderAmount`始终为金额总计。候选快照保存三项匹配小计，结果摘要v2包含箱数。手动试算返回汇总与名单，不持久化可增量更新的候选池；读取规则不计算候选。查询复用已有订单及明细索引，本轮未增加订单明细索引或H5写入汇总维护。详见[ADR-010](adr/ADR-010-lottery-manual-preview-and-weighting.md)。

### 4.7 审计

`audit_log` 记录管理员和系统的敏感操作。审计记录保存变更前后 JSON 摘要、原因、IP、User-Agent 和 trace ID，只追加不更新。

## 5. 精度与计算

| 数据 | 类型 | 规则 |
| --- | --- | --- |
| 元/箱 | `DECIMAL(18,4) NULL` | 保存导入精度；为空时商品可展示但不可订 |
| 明细金额 | `DECIMAL(18,2)` | `箱数 × 元/箱`，HALF_UP 到 2 位 |
| 订单金额 | `DECIMAL(18,2)` | 明细金额求和 |
| 吨箱转换系数 | `DECIMAL(18,8) NULL` | 保存导入精度；为空不阻断展示和下单 |
| 明细/订单吨数 | `DECIMAL(18,6) NULL` | 后端按条件计算；任一明细无法换算时订单总吨数整体为空 |
| 箱数 | `BIGINT UNSIGNED` | 非负整数 |

订单版本明细保存提交时价格、可空的转换系数、可空的折算吨数和商品属性快照；当前订单明细保存当前成交价、当前小计及可空的转换系数、折算吨数和商品属性。订单版本主表保存提交时的客户类型、区域、分公司、经销商名称及可空总吨数快照。看板读取当前 `order_item` 和订单主表金额，历史查询读取 `order_version_item` 快照。商品价格自动同步只更新当前价格和金额，不重新计算吨数；后端忽略前端提交的金额和吨数；任一明细缺少转换系数时不得生成部分订单总吨数。排行看板是展示统计例外：直接汇总有效订单当前 `order_item.line_tons` 的非空值，使可折算商品不被同订单中的缺失系数商品阻断；全部为空时统计结果仍为 `NULL`。

## 6. 关键唯一约束

```text
activity.activity_code
customer(customer_type, normalized_dealer_full_name)
activity_customer(activity_id, customer_type, phone_lookup_hash)
activity_customer(activity_id, customer_id)
activity_product(activity_id, business_key)
activity_product_price_tier(activity_product_id, min_quantity)
customer_order(activity_id, activity_customer_id)
customer_order.order_no
order_version(order_id, version_no)
lottery_draw_attempt(round_id, attempt_no)
lottery_candidate_snapshot(draw_attempt_id, activity_customer_id)
lottery_winner(draw_attempt_id, activity_customer_id)
api_idempotency(activity_id, actor_type, actor_id, endpoint_code, idempotency_key)
```

上述商品和活动客户唯一键按“当前发布版本”解释；若物理表同时保留多个版本，数据库唯一索引需把 `data_version_id` 纳入范围，查询再通过 `activity_data_binding` 限定当前版本。订单和历史快照不能依赖当前商品版本回读。

跨轮次是否排除已中奖客户由轮次规则决定：第一轮不排除，第二轮起可按轮次启用。启用时，应用在持有活动抽奖锁后按活动客户 ID 查询同活动有效中奖结果；每次抽取尝试内的唯一约束保证候选和中奖位置不会重复。重置时旧尝试及结果改为 `INVALIDATED`，新抽取使用递增的 `attempt_no`，因此既能保留旧记录也能合法重抽。

## 7. 关键索引

- 活动：状态 + 开始/截止时间；
- 活动客户：活动 + 客户类型 + 状态；活动 + 分公司；客户类型 + 标准化全称 + 标准化所属分公司唯一；手机号 HMAC 唯一索引；
- 商品：活动 + 客户类型 + 状态 + 排序；物料代码；
- 订单：活动 + 状态 + 最后提交时间；活动 + 客户类型 + 区域/分公司；
- 订单明细：商品 ID + 订单 ID，定位商品调价涉及的明细；
- 订单版本：订单 + 版本号；
- 导入：活动 + 数据类型 + 创建时间；
- 抽奖轮次：活动 + 状态 + 排序；
- 访问事件：活动 + 事件类型 + 时间；
- 审计：活动 + 时间；操作者 + 时间；对象类型 + 对象 ID。

所有列表使用稳定排序和游标/页码分页，不允许无活动范围扫描核心业务表。

## 8. 数据生命周期

- 活动、订单版本、中奖结果和审计默认长期保留；
- 商品和活动客户可使用 `is_visible/is_active` 与 `deactivated_at` 在底层隐藏已从当前版本删除的数据，这些字段不形成后台“停用记录”功能；
- 原始导入文件、导入错误和导出文件保留期可按公司制度配置；
- 导出文件到期可从对象存储删除，但导出任务元数据和审计保留；
- 商品图片只有在无当前商品、订单快照或其他引用后才允许物理清理；
- 测试环境不得复制正式手机号和正式订单。

## 9. 事务边界

### 9.1 订单提交

1. 校验活动绑定和凭证，依次获取活动共享锁和客户独占锁；
2. 规范化请求指纹，检查或创建幂等记录；已完成的 H5 提交直接返回首次响应快照；
3. 新请求检查活动可写状态、商品范围和 `expectedVersion`，锁定订单主记录；
4. 后端计算当前明细；
5. 写订单主表、当前明细、新版本和版本明细；
6. 写订单操作和 outbox 事件；
7. 同一事务保存订单 ID、版本和响应快照并标记幂等完成；事务提交后由 outbox 发布 SSE 通知。

### 9.2 导入确认

1. 导入任务必须为 `PREVIEW_READY`；
2. 同活动同数据类型只允许一个 `CONFIRMING` 任务；
3. 校验预览无阻断错误；
4. 当前应用内任务执行器在非当前数据集内物化并校验新的发布版本；生产环境拆分后由 Worker 承接；
5. 短事务锁定活动 + 数据类型，检查 `base_version` 未变化后切换当前版本指针；
6. 更新任务统计和状态，写审计和 outbox；
7. 最终发布事务失败时当前版本保持不变；发布后的旧版本可按策略回滚。

### 9.3 商品价格自动同步

1. 商品保存事务锁定活动行，并读取商品最新普通箱价和阶梯规则；开启阶梯时 `min_quantity=1` 的独立第一档为实际基础箱价，仅修改普通箱价不触发订单重算；V048 为已有阶梯商品补入原箱价，不改写订单金额；
2. 查询同活动、同商品 ID、状态为 `SUBMITTED` 的订单；
3. 按每张订单中该商品的箱数重新计算当前商品价格和小计；
4. 修改前批量冻结本次变价商品尚未持久化的提交行到 `order_version_item`，已有快照保持不变；当前历史读取合并冻结行和未改行，产生下一版本前补齐全量；更新当前明细、订单总金额和内部锁版本，不新增 `order_version` 或 `order_operation`；
5. 写 `ORDER_PRICE_UPDATED` outbox 事件，提交后由看板刷新；失败时商品和订单更新一起回滚；
6. 重复保存相同价格规则时不更新订单；撤回、作废及其他活动订单不处理。

V047 支持一个商品多个阶梯，以 `(activity_product_id,min_quantity)` 唯一；全部档位共用一种模式。`order_item` 与 `order_version_item` 的可空 `pricing_details JSON` 保存完整阶梯和实际计费段，旧单档列保留兼容；多档分段金额以计费段和 `line_amount` 为准。同步按最多 200 条批量写入，订单/商品线金额按差额更新，只有缺失或需重建的汇总进行全量重建。所有批次在同一商品保存事务完成，不释放活动锁。详情见 [商品多级阶梯价格](08-price-sync.md)。

### 9.4 抽奖

1. 在事务外先取得本实例开奖名额，超额立即返回503；
2. 获取轮次Redis辅助锁，数据库`SELECT ... FOR UPDATE`锁定轮次，校验READY/RESET及前序已完成；
3. 在事务内查询当前匹配小计，按门槛和正权重筛选，生成安全随机结果；
4. 每批250条写完整候选快照，批量写中奖记录并把轮次变为`DRAWN`；
5. 写审计和 outbox 后提交；
6. 提交成功后现场页面才允许揭晓。
