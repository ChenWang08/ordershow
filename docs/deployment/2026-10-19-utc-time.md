## 时间约定

| 层次 | 约定 |
| --- | --- |
| MySQL `DATETIME(3)` | 新数据表示 UTC 的年月日时分秒，字段本身不携带时区 |
| 应用连接 | Hikari 每条连接执行 `SET time_zone = '+00:00'`；驱动指定 UTC、同步会话时区并保留瞬时时间 |
| 数据库默认值 | `CURRENT_TIMESTAMP(3)` 和 `ON UPDATE CURRENT_TIMESTAMP(3)` 在应用的 UTC 会话中生成 UTC |
| Java 读写 | `UtcTime` 将 DATETIME 显式读取为 `LocalDateTime` 再解释为 UTC；写入也使用 UTC `LocalDateTime`，不依赖 JVM 默认时区 |
| API | `Instant` 和 map 查询中的 `LocalDateTime` 均返回带 `Z` 的 ISO 8601 时间；分页、详情、H5 一致 |
| 页面与活动表单 | 显示和输入固定北京时间 `Asia/Shanghai`；表单先按北京时间转换为 UTC 再提交 |
| Excel | 汇总与明细时间统一为 `yyyy-MM-dd HH:mm:ss` 北京时间，表头注明时区；文件名日期也使用北京时间 |
| 过期与调度 | 活动、会话、草稿、幂等保留期和事件可投递时间继续按 UTC 判断 |

`serverTimezone=UTC` 只配置驱动并不足以证明 MySQL 会话已切到 UTC。本次增加连接会话设置，不需要更改整个 MySQL 实例或宿主机时区。部署平台提供的连接参数不能覆盖成 `Asia/Shanghai`。外部 DBA、导入或运维程序如需新增/修改业务数据，也必须在自己的写连接中显式使用 UTC。

## 历史数据处理边界

**本次代码不会批量减 8 小时，也不会在读取时猜测历史记录的时区。** 已混用时区的记录，在完成历史核对前仍可能显示错误；统一 API 格式也不能自动恢复原始时刻。

- 重点核对默认时间字段：`order_change_request.requested_at/created_at`，导入任务创建/更新时间，抽奖规则、轮次、候选、中奖记录创建/更新时间，客户/参会记录创建/更新时间，以及其他表的 `created_at/updated_at`。
- 关注内部记录：`domain_event_outbox.created_at`、`activity_dashboard_snapshot.generated_at`、文件、发布版本、价格同步、商品范围变更与审计创建时间。
- 不能统一平移：订单实际提交/修改时间、审核时间、日志发生时间、事件可投递/已投递时间、登录及草稿过期时间。它们许多写入路径已经显式使用 UTC。
- 活动开始、订货截止、整场结束时间必须按原定业务时间核实；不能因为日期落在某个范围就认定有错。
- 每一批修正清单应保留：表名、主键、字段、原值、目标 UTC 值、来源证据、是否会影响自动更新时间与排序。无可靠证据的记录保留原值，单独确认。
- 修正语句必须限定已批准主键并校验原值，检查影响行数；保留毫秒。更新其他字段可能触发 `updated_at`，需要在演练中明确处理，避免覆盖尚未确认的数据。
- 新旧时间混用可能影响活动、导入任务、审核申请和中奖历史的排序。切换完成前不能把这些列表排序当作历史时刻的证据。
