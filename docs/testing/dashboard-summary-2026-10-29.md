# 看板订单级汇总改造与验收

2026-10-30 更新：本地已部署 `d36cbca`，数据库已到 V041，并开启汇总。最新[部署记录](../deployment/2026-10-30-summary-local.md)和[功能/压测报告](local-summary-validation-2026-10-30.md)为当前状态依据。本文前半部分维护规则已同步 V041；后半部分保留 2026-10-29 的失败记录与当时“未部署”结论，不把历史失败改写为成功。

## 数据与读取规则

V040 新增 `order_dashboard_stat`、`order_dashboard_product_line_stat`。前者一单一行，保存明细数量、原始吨数和吨数榜使用的有效吨数；后者按订单、原始可空项目组、是否礼盒分组，保存金额和数量。所有计算使用数据库 DECIMAL。主表金额、数量、客户身份和最后提交时间仍从 `customer_order` 读取；TOP5 的吨数仍读原主表字段，SKU 仍在原始明细上去重。

V040 曾通过逐明细触发器标记 dirty；V041 已删除这三个触发器，不修改已发布的 V040。当前启用汇总时，正常下单/后台调整在批量明细写完后，由 `DashboardSummaryStore.refresh` 按订单标脏并重建；价格与吨数同步也沿用业务事务内的维护路径，失败整体回滚。归档活动可维护统计副本，但不改变冻结的历史展示快照。状态变化仅改变主表筛选，不需要重复计算商品汇总。关闭汇总时 `refresh` 直接返回，裸 SQL 修改明细也不会自动标脏。

读取按订单二选一：干净的汇总参与计算；缺失或 dirty 的订单从原始明细计算。两支使用 UNION ALL，保证不会重复计数。活动与客户筛选在明细读取前限定范围。无明细、缺换算、有效零、NULL 与真实“其他”标签继续沿用原 SQL 规则；吨数公司榜与分公司榜的过滤位置保持原样。

实时统计使用一个 REPEATABLE READ 事务，历史快照缺失时仍允许写入；已存在的调用方写事务保持原事务边界。没有跨请求 TTL 缓存，没有依赖事件 MAX(id) 判断数据是否有效。接口、前端手动刷新、已有历史快照格式不变。

原查询路径可通过开关恢复。`DashboardBeforeSummaryReference` 是改造前源码的测试副本，只用于差分对照，不进入生产包。

## 开关与迁移前提

- 源码/Compose 兜底默认 `DASHBOARD_SUMMARY_ENABLED=false`：读取原始明细，正常业务写入不维护汇总。本地 2026-10-30 部署已在 `.env` 持久设为 true。
- `DASHBOARD_SUMMARY_ENABLED=true`：启用事务内同步维护、汇总读取及缺失/dirty 回退。
- `DASHBOARD_SUMMARY_ACTIVITIES=12,34`：只让指定活动读取汇总；留空表示所有活动。当前 `refresh` 只检查总开关，不按此白名单限制维护范围。
- 回退读取：设置 enabled=false 并按正常发布流程应用配置，不删除副表或业务数据；这不是回退程序版本或数据库结构。
- V040 不自动回填，不修改订单、历史版本或历史展示快照；既有数据可直接回退原始查询。
- 关闭期间有订单写入，旧汇总可能仍是“干净”标记但内容已过时。重新开启前暂停写入，对受影响活动执行 `repair` 和从 0 开始的 `check`，确认一致后再启用，不能依赖缺失/dirty 回退自动发现这类旧值。

从 V039 升级仍须执行 V040（创建触发器）再执行 V041（删除触发器），因此创建触发器的权限要求仍不能省略。应用支持通过 `DB_MIGRATION_USERNAME`、`DB_MIGRATION_PASSWORD` 提供独立 Flyway 账号；必须显式注入执行迁移的进程，当前业务 Compose 不会仅因 `.env` 新增这两个变量就自动传入。2026-10-30 本地采用一次性迁移容器执行升级，日常后端仍使用 `order_show` 账号。不得给日常账号授予 SUPER，也不修改全局日志信任设置。

MySQL DDL 不整体回滚；迁移失败必须先检查本次新对象和 Flyway 失败记录，再按迁移恢复流程处理，不可直接反复重启。完整升级至 V041 后不再保留这三个触发器；若中途停在 V040，需另外检查实际触发器及其 DEFINER 状态。

## 回填、对账、修复

显式服务端 CLI，不启动 HTTP、定时任务或自动迁移，使用明确设置的 DB_URL / DB_USERNAME / DB_PASSWORD：

```text
java -Xms32m -Xmx128m -Dloader.main=com.fengyi.ordershow.maintenance.DashboardSummaryCommand \
  -cp /app/app.jar org.springframework.boot.loader.launch.PropertiesLauncher check 12
```

将 `check` 换成 `rebuild` 或 `repair` 可重建统计。在当前 V041 对应代码中，两者都会遍历指定范围内的订单并调用会主动标脏的 `refresh`，不要假设 `rebuild` 会跳过现有干净行；关闭后重启汇总的维护流程统一使用 `repair`。可增加第三个参数 `afterOrderId` 从上次游标继续。每批200单，每单一个短事务，锁定活动与订单后再读取明细，避免旧回填覆盖新提交。遇到短暂锁冲突最多重试3次。操作不会修改订单、历史版本、历史展示快照。

`check` 在每单的一致视图内逐字段核对明细数、两类吨数、项目组/礼盒金额数量，并检查缺失、脏标记、重复和多余分组。返回订单ID与差异原因；存在差异则退出非零。不同订单的检查时点允许不同，因此这不是整个活动停写快照。回填结束后再次从0开始对账，再启用汇总读取。V041 下直接修改明细的维护 SQL 不会自动标脏，必须配套修复与对账；不要直接编辑统计副表或改写已发布迁移。

### 本轮追加：草稿并发修复（用户确认方案后）

以上死锁记录发生时尚未修改草稿业务代码；随后按确认方案增加专项修复，不改V010表结构、唯一约束、隔离级别或业务规则。

- `OrderDraftWrites` 在既有“活动共享锁→客户排他锁”保护下，先按活动/客户查询主键，已存在时按主键更新、缺失时普通INSERT，移除草稿upsert；删除先查主键，缺失不执行DELETE。正常更新仍递增草稿版本，过期草稿仍可按原规则更新。
- 保存、主动删除和提交后删除共用这套写入方式。订单提交/变更申请与删除草稿仍同事务，不拆成异步操作。
- `DraftSaveTransactions` 外层不持事务，每次执行完整READ_COMMITTED事务；仅当MySQL错误码1213且SQLSTATE=40001时，完整回滚后重试，最多3次。等待分别20–50ms、50–100ms，发生在事务外。每次重新检查身份、商品权限、活动状态和订单版本。
