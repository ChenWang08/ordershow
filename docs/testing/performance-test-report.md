## 当前结论

初测发现50用户高频混合流程已超过响应时间门槛，不能宣称1000/2000在线目标已验收。
固定到达率模型下，10次完整流程/秒连续3分钟通过；20次/秒出现大量丢弃迭代及延迟超标。
这些是当前限额环境和数据模型下的实测点，不是全系统最大在线人数或长期稳定容量认证。
10用户基准通过。两者均为每轮读取300商品、查询订单、保存草稿、修改10个商品、停顿1秒的负载模型。
用户数不能换算成实际活动同时在线人数；报告中的请求速率和数据规模必须一并使用。

## 环境

- 项目：order-show-load；API：127.0.0.1:8280/api/v1；构建当前后端源码。
- Docker可见32逻辑CPU、约7.56GiB内存；与本机业务共享宿主机。
- 后端限2CPU/1280MiB，堆256～768MiB；MySQL限1.5CPU/1GiB；连接池20。
- Redis限128MiB，MinIO限256MiB；k6 1.6.0限2CPU/1GiB。
- MySQL和MinIO使用专属持久磁盘卷，无业务数据卷挂载。
- 两个测试活动、600商品、2550虚构客户；主活动300商品/2500客户。
- 当前容量夹具使用SPECIAL客户/商品、无图片、无阶梯价。综合客户大区和分公司限制、阶梯优惠性能需要另行扩展。
- 目录和会话使用SQL夹具；历史订单通过真实H5接口生成1000笔。图片为空，未覆盖静态资源下载。
- 历次写入保留历史版本；数据规模持续增长，各档不是重置后的严格单变量比较。

## 已捕获的瓶颈证据

1. 商品目录逐商品查询图片、分公司范围和阶梯价。300商品增加约900次附属SQL往返。
   代码：backend/src/main/java/com/fengyi/ordershow/catalog/ProductCatalogReader.java，withImages。
   数据库语句汇总中三类附属查询各已执行数十万次。
2. 订单提交持有活动行排他锁。实时采样中活动行出现4条X锁等待、12条S锁等待，data_lock_waits共65条等待关系。
   代码：order/OrderRepository.java:lockPricing。草稿/审计外键检查也可能等待该活动行；这是结合锁采样与语句耗时的解释。
3. 当前订单读取包含全部历史版本，再逐版本查询明细。反复修改会增加SQL次数和响应体。
   代码：order/OrderRepository.java:order、withVersionItems。压测期间history查询明显累积。
4. 50用户Hikari活跃连接达到20，待连接线程峰值31；MySQL接近1.5CPU限额，k6峰值约25.8%单核，未见压测工具CPU饱和。
   本档数据库行锁等待计数增加5208次，累计等待时间增加1857274ms（多事务累计，并非墙钟时间）；慢查询计数增加3661。
5. SSE客户端关闭后，通用异常处理器尝试向text/event-stream响应写ProblemDetail，产生转换异常日志。应单独处理已断开的流。

优先建议：批量加载商品附属数据；拆分当前订单和分页历史接口；缩短活动级锁持有时间并验证调价一致性；再评估数据库CPU和连接池配置。
本轮仅添加测试资产，不修改业务代码，不把猜测的优化收益当作实测结果。
