# 性能测试执行计划

## 范围与环境

目标是测量当前实现的稳定吞吐、响应时间、错误率和并发正确性。
1000人在线及2000人峰值是待验证目标，不是已有容量结论。
HTTP压测使用k6；SSE、数据生成、并发语义和数据库核对使用Node脚本；环境固定为order-show-load。
执行方法见 [tests/load/README.md](../../tests/load/README.md)。

## 执行步骤与阶段门槛

1. 检查Docker/硬件/业务容器，构建独立限额环境及专属磁盘卷。
2. 生成两活动、每活动300商品，主活动2500客户、辅助活动50客户；会话按客户隔离。
3. 验证10路幂等重放、10路同版本竞争、活动隔离、手机号登录及金额/版本一致性。
4. 5用户2分钟冒烟，准备1000笔真实订单。
5. 10、50用户各3分钟基准；100、200、500、1000用户各5分钟阶梯；再测1500、2000峰值。
6. 固定迭代到达率测吞吐，1/10/50商品明细测写入复杂度，SSE 10/50/100连接专项。
7. 后台分页/搜索/筛选/导出、商品调价；两活动混合负载。
8. 已达标配置执行突发流量及60分钟稳定性，再在独立环境执行Redis/后端恢复。
9. 测后核对，输出报告，停止专属服务保留数据和报告。

读、写、看板各自逐级评估。任一场景失败先停止该场景升压，查明瓶颈。
数据错误或明显资源耗尽立即停止负载；压测机饱和不得归因于后端容量。
若目标负载未通过，峰值/长稳/恢复等尚未执行项必须在报告中标注，不宣称完整验收。
5000/10000订单数据档、真实图片下载、正式网络入口、浏览器渲染应在容量初测后独立扩展；当前夹具上限不支持10000笔唯一客户订单。

## 指标

读P95≤500ms，写P95≤1500ms，P99≤3000ms，正常请求失败率<1%，金额/客户/版本错误为0。
SSE通知目标3秒；页面完整更新另行验收。导出按订单数、字节数、耗时独立评价。
统计用户数、实际请求速率、成功提交速率、错误、丢弃迭代；采集JVM/GC/Hikari、容器资源、MySQL慢查询及锁等待。
预期版本冲突仅在独立正确性测试中排除，正常混合负载冲突属于失败。
所有结果记录镜像、代码版本、资源限制、数据规模、测试时长和局限。
