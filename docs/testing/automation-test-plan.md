# 订购会系统自动化测试计划与用例清单

> 文档状态：测试设计基线  
> 编制日期：2026-08-27  
> 适用范围：当前仓库中的 React/Vinext 前端、Spring Boot 后端、MySQL、Redis、MinIO 及 Docker Compose 本地实现

## 1. 测试目标

本计划用于证明系统不仅“页面可打开、代码可编译”，而且主要业务规则在真实依赖环境中能够重复验证。核心目标如下：

1. 验证商品、白名单和现场到场的全量导入、预览、发布及版本切换正确；
2. 验证活动从草稿到发布、开始、截止的状态控制正确；
3. 验证 H5 身份识别、下单、修改、撤回和重新提交形成完整闭环；
4. 验证金额、数量、吨数、订单版本、排行和专题战报的数据口径一致；
5. 验证抽奖候选、去重、防重复、结果持久化和重置留痕正确；
6. 验证活动隔离、权限、CSRF、幂等、乐观锁、手机号保护和审计边界；
7. 形成一条可在干净环境重复执行、执行后不污染现有业务数据的测试流水线。

本计划不是生产压测、灾备演练和正式数据验收的替代品。生产域名、HTTPS、云端高可用、备份恢复和现场网络仍需单独验收。

## 2. 测试原则

- 测试数据库与当前 `order-show-mysql` 数据卷完全隔离；自动化测试不得连接或清理现有业务数据库。
- 集成测试优先通过公开或管理员 API 准备业务事实，避免绕过加密、审计和版本规则直接写表。
- 只有难以通过公共入口构造的基础条件才使用测试 fixture/seed，并集中在测试支持代码中。
- 使用脱敏虚拟手机号、虚拟经销商和小型 Excel/ZIP，不复制真实客户信息。
- 时间判断使用后端可注入的 `Clock`；测试不得依赖执行当天或长时间等待定时任务。
- 每个测试独立创建数据或在事务/容器级清理，不依赖用例执行顺序。
- 断言同时覆盖 HTTP 结果、数据库业务事实和必要的审计记录；不能只断言页面文案。
- 采用等价类、边界值和高风险规则选取场景，不穷举无意义的字段组合。

| 层级 | 建议工具 | 主要职责 | 是否使用真实依赖 |
| --- | --- | --- | --- |

| API 集成测试 | Spring Boot Test、Testcontainers、REST Assured/MockMvc | Flyway、认证、活动、导入、订单、看板、抽奖、审计 | MySQL/Redis/MinIO |

## 4. 隔离环境与生命周期

### 4.1 默认方案

后端集成测试使用 Testcontainers 创建临时 MySQL、Redis 和 MinIO：

1. 测试启动时创建容器和随机数据库；
2. Spring Boot 连接临时依赖并自动执行全部 Flyway 迁移；
3. 测试代码生成管理员和测试活动，导入 fixture；
4. 执行 API、数据库和审计断言；
5. 测试结束后停止并删除容器及临时数据。

默认关闭 Testcontainers reuse，确保每次从干净环境开始。Maven 依赖缓存可以保留，它不包含业务数据。若测试进程异常退出导致容器残留，只允许按测试容器标签定向清理，禁止删除项目现有 Compose volume。

### 4.2 浏览器 E2E 环境

E2E 使用独立 Compose project name，例如 `order-show-e2e`，并使用随机或专用端口。测试结束执行对应项目的 `docker compose down -v`，只删除 E2E 专属 volume。不得对默认 `order-show` 项目执行带 `-v` 的停止命令。

### 4.3 固定测试时间

建议将后端所有业务当前时间统一改为注入 `java.time.Clock`：

- 固定基准时间：`2026-08-27T08:00:00Z`，即北京时间 `2026-08-27 16:00:00`；
- 待开始活动：开始时间为基准时间加 1 小时；
- 进行中活动：开始时间为基准时间减 1 小时，截止时间为基准时间加 1 小时；
- 已截止活动：截止时间为基准时间减 1 秒；
- 边界用例可精确推进测试时钟，不等待真实分钟调度。

## 5. 测试数据设计

### 5.1 测试活动

| 编号 | 状态/时间 | 用途 |
| --- | --- | --- |
| `e2e-draft` | DRAFT | 导入、编辑、发布前校验 |
| `e2e-scheduled` | 已发布，尚未开始 | 未开始限制、撤回发布 |
| `e2e-active` | 已发布且处于时间窗内 | H5、订单、看板、抽奖主流程 |
| `e2e-closed` | 已截止 | 全部写操作只读校验 |
| `e2e-other` | 独立活动 | 跨活动越权和数据隔离 |

自动化实现时每个测试可以只创建所需活动，不要求长期保留以上全部活动。

### 5.2 虚拟客户

手机号使用明确的测试号码段，只存在于临时环境。建议至少包含：

| 客户 | 类型 | 大区/分公司 | 特征 |
| --- | --- | --- | --- |
| G01、G02 | 综合 | 东区/上海分 | 正常客户、同分公司简称匹配 |
| G03 | 综合 | 南区/广州分 | 无订单客户 |
| G04 | 综合 | 北1区/北京分 | 后续撤回订单 |
| S01、S02 | 特渠 | 不使用综合大区筛选 | 正常客户 |
| GS01-G、GS01-S | 综合、特渠 | 分属两个通道 | 同手机号跨通道合法 |
| DUP01、DUP02 | 同一客户类型 | 任意 | 同手机号导入阻断 |
| NAME01、NAME02 | 同分公司相同/相近名称 | 任意 | 到场关联冲突 |

客户名称统一添加 `AUTOTEST_` 前缀。任何测试失败信息、日志和大屏响应不得出现完整手机号。

| 商品 | 特征 | 预期用途 |

| P02 | 综合、有效元/箱、吨箱系数为空 | 总吨数整体为空 |
| P03 | 综合、元/箱为空 | 展示但不可下单 |

### 5.4 Fixture 文件

计划新增以下脱敏、小体积文件：

```text
backend/src/test/resources/fixtures/
├── products-valid.xlsx
├── products-warning.xlsx
├── products-blocked.xlsx
├── whitelist-valid.xlsx
├── whitelist-duplicate-phone.xlsx
```

每份文件只保留覆盖规则所需的最少行数。Fixture 本身属于测试资产，测试结束后保留在仓库；由 fixture 生成的数据库记录和对象存储文件随临时容器删除。

## 6. 优先级和准入标准

- `P0`：订单与数据正确性的上线阻断项，每次提交或合并必须执行。
- `P1`：关键异常、安全、导入、抽奖和并发项，进入现场演练前必须通过。
- `P2`：性能、恢复、兼容性和低频边界，版本发布前或定期执行。

开始自动化实现前应满足：Docker 可用；测试密钥为非生产值；fixture 不含真实个人信息；测试连接串明确指向临时容器；所有破坏性清理都能通过 Compose project name 或容器标签限定范围。
