> 本文记录首次 UTC 代码回归，新写入验证不足以覆盖历史混用时区。后续实际历史副本、校正回退、真实 Excel 与三个浏览器时区的补充结果见 [历史时间回归](time-history-2026-10-19.md)。补充回归当时共 226 项 Node 测试通过；本地历史工具及其 3 项测试随后移出归档，项目常规测试为 223 项。未确定默认时间字段仍保留，不宣称全部历史问题已解决。

## 测试范围

- 前端 `tests/time.test.mjs` 在独立进程中分别设置北京、UTC、美国洛杉矶时区，执行真实时间工具和活动 API 转换：统一显示、无时区 UTC 兼容、表单回填、创建/编辑/重新开放提交、凌晨文件名、跨年、闰年、美国夏令时切换日与非法日期。
- Java `UtcTimeConfigurationTest` 验证不同 JVM 时区下 typed 查询与 map 查询返回相同 UTC 时间、空值处理和北京时间导出格式。
- `UtcDatabaseIntegrationTest` 仅使用隔离 `order_show_e2e` 数据库的临时表，加载实际 application.yml 的 Hikari 参数，验证数据库默认时区与 JVM 时区不同情况下，应用会话、默认创建时间、自动更新时间、显式时间写入/读取、map 查询及过期条件。
- `OrderExportServiceTest` 读取真实生成的 XLSX，核对汇总与商品明细的北京时间一致，同时保留原有金额、电话、阶梯价、空值和工作表结构检查。
- 原有隔离 API E2E 新增真实 H5 申请、后台分页、详情、H5 当前申请时间一致性与实际 UTC 当前时间检查；通过和驳回后审核时间不早于申请时间。原有活动状态、草稿、登录、幂等和订单测试继续运行。
- 压测 SQL 连接也设置 UTC。长稳监测拒绝负的通知年龄；outbox 核查拒绝负的通知年龄或投递延迟，避免错误时区掩盖超时。
- `scripts/test-time-browser.mjs` 在三个真实 Chromium 时区下登录隔离系统，核对活动表单、审核列表/详情、H5 订单时间和看板更新时间；只读业务记录，不提交活动或订单修改。

## 运行

```powershell
node --test tests/time.test.mjs
npm test
npm run typecheck
npm run lint
.\scripts\run-automated-tests.ps1 -KeepEnvironment
$env:ORDER_SHOW_E2E = 'order-show-e2e'
# 本机没有 playwright 包时，按 tests/README.md 指定已安装的 ORDER_SHOW_PLAYWRIGHT_MODULE。
node scripts/test-time-browser.mjs
```

一键脚本只启动固定项目 `order-show-e2e`，测试入口为 3100/8180，数据库为 33306 的临时测试库。Java 数据库专项测试由同一脚本设置的 `ORDER_SHOW_E2E=order-show-e2e` 启用，只创建连接级临时表，不操作业务库。测试结束后按项目既有方式运行 `scripts/test-env.ps1 reset`。
