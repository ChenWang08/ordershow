# 启动预热、同步批量审计与负载复测（2026-09-08）

后续虚拟线程/H5写入隔离及全新环境A/B见[2026-09-10高频优化报告](high-frequency-admission-report.md)；本页保留此前阶段结果。

## 范围与实现

负载只施加到`order-show-load`，不降低持久化配置、不扩大后端2CPU/1280MiB、MySQL1.5CPU/1GiB、20个数据库连接及40个HTTP工作线程，不放宽原延迟/错误门槛。

- 新增启动只读预热：选最多4名当前有效活动/白名单客户，最多32轮，执行商品读取、轻量当前订单读取及JSON序列化。轮间检查15秒预算，单个读取事务超时3秒；不是严格15秒墙钟上限。无客户则跳过，无虚构订单/登录会话，不缓存身份或价格。
- 显式执行顺序：手机号迁移、业务初始化、可选价格回填、只读预热；预热异常阻止成功启动，不静默标记就绪。
- 业务过滤器在Spring就绪前和停止接流量时返回503与Retry-After；健康端点保持可用。Docker健康检查改用readiness，前端等待后端健康。就绪之前的503不计作“已成功接单”，不能用就绪门槛隐藏启动耗时。
- 同步审计合并：由正在处理请求的线程收集同批记录、显式事务提交，每批最多100条，待处理队列最多256条；没有独立后台队列，也不提前返回审计调用。队列满时同步直接持久化，不丢弃。
- 保留审计发生时间与全部字段。确认的约束错误整批回滚后逐条隔离；未知连接/提交错误不盲目重放，保持原AuditService的记录失败日志语义。
- **审计仍在原MVC afterCompletion位置，不与订单事务原子提交，也不保证客户端收到HTTP响应之前审计必已落库。** 本轮没有承诺审计恰好一次或进程强杀下绝不丢失。新增压测trace_id及审计计数/去重核对，监测正常运行是否缺失或重复。

## 千人首次下单发现的订单号碰撞

一分钟千人进入`peak-entry-100-1788854559573`通过：1000名客户完成，2000请求无错误，验证P95 23.64ms、商品6.23ms、完整流程30ms。

首次下单`peak-order-100-1788854628518`未通过：1000人启动，999成功提交，1次HTTP500；999新增版本一致，1000条审计含1条失败完整无重复。失败trace为`peak-order-100-1788854628518-96-1-submit`，日志确认`customer_order.uk_order_no`冲突，订单号`ZY2026090808040101CFD3`重复。不是负载超时或重复客户；原生成器仅使用UUID前4位，同一秒同活动随机空间只有65536。

当时暂停长稳并修复生成器：保留ZY前缀，完整UUID以Base36编码，最长27字符，适配既有VARCHAR(64)，不修改已有订单号或数据库结构。新增固定UUID尾部差异/完整位数保留及10000个突发生成测试。不把随机测试当数学唯一性证明，数据库唯一约束继续保留。

修复后完整后端108项测试通过、无跳过。原失败客户索引195用原幂等键重试成功，再次重放不新增版本；确认失败事务原先已回滚。该恢复验证不改变原峰值999/1000失败结论。
