# H5高频读取与启动突增负载优化（2026-09-08）

## 范围与诊断

仅在`order-show-load`隔离环境施加负载。200个用户重复读取300个商品、读取轻量当前订单、保存10项草稿、提交10项订单，每轮停顿1秒。不是200人仅保持在线，也不是浏览器页面加载测试。

保持后端2CPU/1280MiB、MySQL1.5CPU/1GiB、数据库连接池20，不放宽读取P95≤500ms、写P95≤1500ms及错误中止门槛。

- 本轮旧镜像未业务预热的基线`mixed-200-1788849645408`：约32秒按错误门槛中止，HTTP失败1.19%，读P95 6351ms。连接池20个连接全占用，采样等待峰值173，CPU接近限额。
- 中止时605次客户端确认、648次数据库提交；全部648个原幂等请求重放通过，没有新增订单/版本，金额数量不变。原始失败和重放报告均保留。
- 同一旧镜像预热后基线`mixed-200-1788849800720`：2分钟8810次提交、无HTTP错误，读P95 790.64ms。商品P95 890.14ms、当前订单599.81ms、草稿991.03ms、提交1012.12ms，读取不达标。
- 冷负载中途SQL采样显示明细逐条INSERT数千次；COMMIT和审计INSERT的累计数据库耗时也较高。不能仅凭此断定唯一根因；CPU饱和、连接排队、落盘均需区分。没有取消审计或降低数据库持久化配置。
- H5草稿已有800ms防抖，当前订单已使用`includeHistory=false`；本轮不重复修改这些功能。

## 实施

- 当前订单明细与历史明细改为每批最多100行的JDBC批量写入，启用MySQL驱动`rewriteBatchedStatements`，减少逐行数据库往返。
- HTTP工作线程默认上限40（可用`HTTP_MAX_THREADS`配置）；不是限制在线用户为40，SSE异步连接不会持续占用一个工作线程。该默认依据本机2CPU、20连接的测试选择，并非所有服务器的通用最优值。
- H5商品查询直接关联当前发布绑定，省去单独读取版本ID；当前订单直接按活动和客户查询主记录，省去先查订单ID。保留分公司/客户类型/活动权限过滤，不引入可能陈旧的价格或身份缓存。
- 所有批次继续使用原事务；保留锁顺序、商品/价格校验、幂等键、当前版本及历史快照。批次异常向上传播，不吞掉失败或提交部分订单。
- 新增字段、空值、顺序、分批边界测试；真实MySQL测试使用连接私有临时表，检查分批写入及后续批次失败时整个事务回滚，不改真实夹具明细。
- 压测监控增加连接占用时长、SQL摘要前后快照和逐接口延迟输出。
- 新增4项批量写入单元/真实MySQL测试通过，包括201行跨三批、增量阶梯价格/空图片快照、第二批故障时当前和历史明细均回滚。初版临时表同名LIKE建表失败，仅为测试夹具问题，已修正并复跑通过。
- 最终完整后端97项测试全部通过、无跳过，包含10项隔离API E2E、真实MySQL锁/批量事务测试以及新增H5读取作用域测试。压测入口ESLint、Node语法检查通过。前端本轮未改动，未重跑浏览器视觉验收。

## 结果

仅批量写入、仍200个HTTP线程、未业务预热的`mixed-200-1788850079403`：2分钟7387次提交且版本对账一致，5次HTTP失败（0.0169%），读P95 1491ms，仍不达标。MySQL摘要确认约7387次多行INSERT各写10行，批量改动实际生效，但不足以单独解决问题。

批量写入加40个HTTP工作线程、未业务预热的`mixed-200-1788850305156`：2分钟7961次提交，31844次HTTP全部成功，版本一致；读P95 1088.86ms、写P95 1233.34ms，但P99仍超过3秒，整体延迟仍不通过。没有把服务器端排队从客户端计时中扣掉，也没有增加数据库连接数。

这里“冷”仅指新启动后端未执行H5业务预热，不代表清空数据库缓存或整台机器冷启动；各轮持续累积历史数据，不是完全相同快照的严格A/B实验。

40线程预热段`mixed-200-1788850452327`：2分钟9706次提交、38824个HTTP无错误，综合读P95 490.26ms、当前订单456.17ms、商品517.32ms、写638.11ms。商品单项仍失败，不能用综合读达标覆盖单项失败；随后继续优化上述两处读取往返。

最终版本未业务预热`mixed-200-1788850899534`：2分钟7549次提交、30196个HTTP无错误，版本对账一致；综合读P95 1198.56ms、商品1300.21ms、当前订单1096.35ms，写P95 1317.38ms。读取P99 4365.96ms、最大6678.63ms，启动延迟仍失败。两轮40线程新进程测试均未再出现HTTP失败，但不代表已经证明所有冷启动条件下都不会超时。

**最终读取门槛仍未通过，不升级500/1000用户高频测试。** 与前轮同为5分钟、100订阅者的761ms相比，综合读P95下降约21%，写P95由989ms降至764ms；提交流程由73.69次/秒变为71.69次/秒，没有证明容量提升。数据库历史数据增长和共享宿主机影响仍在，不能视为同快照严格A/B。

最终5分钟采样：连接等待最大20（旧冷基线173、旧暖基线125），应用CPU采样最大约72.75%。SQL摘要前后差值中，审计INSERT平均39.06ms、COMMIT平均24.39ms，而商品主查询平均4.30ms。摘要抓取不是原子快照，计数会有边界差异；累计数据库等待是多连接相加，不是测试墙钟时间。剩余瓶颈线索更偏向写入持久化和连接/工作线程排队，尚不能据此断言全由本机磁盘导致。下一步优先做独立压测机/目标部署存储的对照，以及保持审计可靠性的持久化设计评估，而不是盲目扩大线程或缓存客户权限/成交价格。

商品纯读取对照`read-200-1788851435143`：200用户1分钟，11824次请求、193.85请求/秒，无错误，P95 79.90ms、P99 199.41ms，通过全部门槛。这支持“混合高频写入下共享资源竞争”这一判断，但不能凭单次对照证明唯一根因。

最终业务正确性专项通过：金额/数量、版本连续性、明细计算、未完成幂等记录错误数均0；10次相同幂等键并发重放、同版本并发修改、跨活动隔离及两场看板核对通过。以上写入均在隔离夹具中进行。
