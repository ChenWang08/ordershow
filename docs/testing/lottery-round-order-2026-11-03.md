# 抽奖轮次排序：实现与定向验证

日期：2026-11-03。状态：源码完成，未部署；仅验证本次相关功能，无全系统回归或整体压测。

## 业务规则

- 从未开奖的草稿与已发布 READY 后缀可排序；DRAWING、DRAWN、COMPLETED、RESET 或 currentAttemptNo>0 的轮次及其之前的位置固定。
- 活动结束、归档或规则归档时禁止调整。禁止跨规则、缺失、重复或额外 ID。
- 排序只改变 round_no，轮次 ID、名称、奖品、图片、筛选、中奖人数、重复中奖设置和历史开奖记录不变。列表序号代表执行位置，不自动修改名称。
- 重复中奖开关跟随轮次保存；首轮仅在候选计算时视为不涉及历史中奖，不将其原开关自动改写为false，避免再次移到后续位置时丢失设置。
- 已保存规则有未保存编辑/增删时，先保存再排序；全新未发布草稿在本地排序，随原保存操作提交。
- 仅手柄可拖动，支持键盘上下方向键及上移/下移按钮；锁定轮次仍能点击查看。

## 实现

### 保存与并发

- V050 仅给 lottery_rule 增加 revision，默认0；不回写历史轮次或开奖。db/schema.sql 同步该字段。
- 独立 GET/PUT `/admin/activities/{activityId}/lottery/rules/{ruleId}/round-order` 返回/保存轻量顺序。PUT 接收 expectedRevision 和全部 roundIds，不接收配置或候选数据。
- 顺序不变时前端不提交；服务端在版本一致时同序重放不写数据库、不重复成功审计。旧版本即使顺序相同仍返回409，避免将新版本号关联到旧配置。网络结果不确定时读取已保存规则核对，失败则暂停写入并提供显式重新加载入口，不盲目重试保存。
- 正常成功保存读取一条活动状态、当前规则及本规则轮次位置，位移行通过临时安全序号及最终序号两批更新，避开唯一键冲突；只有最终写入增加轮次 lock_version。新增一条同事务审计，保存调整前后 ID 顺序。
- 排序、规则保存、发布、开奖、完成及重置使用规则行锁在先的顺序。NOWAIT 锁忙立即409，不新增 Redis 锁，不长时间排队；不为排序锁订单、白名单或活动行。
- 普通配置保存携带 expectedRevision 和与配置一一对应的 roundIds；已保存轮次按 ID 更新，删中间轮次不会把后面的配置覆盖到其他 ID。配置保存不接受隐式重排。
- 规则配置、排序、发布及开奖状态变化推进版本；过期写入返回 LOTTERY_RULE_CHANGED。排序成功通过专用回调清除编辑标记，不改变商品选项/中奖统计查询的刷新键。
- 开奖请求携带 expectedRevision；旧大屏被拒绝时读取最新资料并要求工作人员再次确认，当前请求不开奖。完成一轮后按需读取一次最新抽奖资料，再选择下一轮，兼顾排序和其他配置变更。
- 切换活动时重新挂载设置组件；旧保存及迟到响应不覆盖另一活动。

### 请求及资源范围

- 拖动过程中0个网络请求；正常有效落下1个排序 PUT。移动取消/原位落下0个请求。
- 排序不调用候选试算、商品选项、中奖统计、订单查询或汇总重算。已有试算只失效，下一次仍需点击手动试算。
- 排序不写 domain_event_outbox，避免现有全活动 invalidate 广播；只记录审计并标记日志模块下次打开时更新。
- 不新增轮询、长连接、后台任务、订单索引或下单写入工作；保留既有模块进入读取及其他页面已有的行为。
- 时间、并发限制和连接池配置不变；没有修改部署环境配置。

## 真实 MySQL 定向验证

用户授权后在本机 Docker 29.8.2 的 Linux 环境运行，使用缓存的 mysql:8.4 和 maven:3.9.11-eclipse-temurin-21；没有构建业务镜像。固定测试项目 order-show-lottery-test、端口33316、数据库 order_show_lottery_test，MySQL数据位于临时内存文件系统，未挂载业务数据卷。MySQL上限1GB内存/1.5CPU，测试运行器上限1.5GB/2CPU；Maven堆256MB、测试JVM堆512MB。

4个真实SQL用例均通过，无跳过：

1. 重排保留历史中奖及结果摘要，并严格按新顺序开奖，拒绝旧版本。
2. 审计插入失败时轮次顺序和版本一起回滚。
3. 另一事务持有规则锁时立即拒绝排序。
4. 重排后删除中间轮次仍保持配置所属 ID，拒绝重复旧保存。

这些用例通过真实连接和独立事务执行，迁移从空测试库到V044，插入旧规则，再升级到V050。仅选择 `LotteryIntegrationTest#reordering*`，没有运行该类其他抽奖功能或全系统回归。

首次执行发现锁忙错误转换缺陷：MySQL NOWAIT返回3572/HY000，当前Spring将它包装为UncategorizedSQLException，原先仅捕获CannotAcquireLockException会使接口返回500。已将抽奖规则行锁的3572统一转换为409 LOTTERY_RULE_BUSY，其余SQL错误原样保留；新增单元用例区分3572和1064，修正后8个排序单元用例和4个数据库用例全部通过。首次失败及修正后的原始报告均保留。

## 排序 HTTP 耗时验证

LotteryOrderHttpTest使用真实Tomcat、正式LotteryController/GlobalExceptionHandler/TraceFilter、事务代理LotteryService、JDBC/Hikari和上述MySQL，端口由测试运行器随机分配且只绑定其内部回环地址。仅注册排序所需组件；管理员身份及无关服务使用替身，未加载完整应用、认证链、定时任务或业务服务。测试连接池最大4/最小1，仅对该测试上下文生效。

12轮、100轮分别预热10次，再计时50次顺序PUT。每次都将首轮移到末尾，全部位置发生移动，包含HTTP往返、JSON处理、数据库更新、审计及事务提交；不把迁移、创建规则、发布、预热计入耗时。P95取排序后的第48/50个样本。每次校验返回顺序与版本，结束核对配置所属ID未变、每次成功仅一条排序审计、无新增outbox及候选/开奖/中奖记录、无Redis或文件服务运行时调用。

每种轮次数另执行3个预期失败请求：旧版本同序重放409、另一真实连接持有规则锁时409、审计触发器故障500；核对顺序及版本未被失败请求改变。测试工具曾误将Spring初始化替身的调用计入运行期，已将观测起点调整到上下文初始化完成后，只复跑HTTP专项；不涉及产品逻辑修改。

最终结果（毫秒）：

| 轮次 | 计时成功/请求 | 中位数 | P95 | 最慢 | 非预期错误 |
| --- | --- | --- | --- | --- | --- |
| 12 | 50/50 | 39.87 | 72.79 | 93.48 | 0 |
| 100 | 50/50 | 68.11 | 97.68 | 106.81 | 0 |

两个规模的排序成功请求P95均低于本次300ms目标。12/100轮的锁忙HTTP请求分别396.77/15.04ms，在持锁连接尚未释放时返回409，没有等该事务完成；旧版本拒绝分别106.71/16.56ms。审计故障请求分别79.68/85.76ms返回预期500，顺序、版本及成功审计数均保持故障前状态。该6次故意制造的失败请求不计入成功排序耗时。
