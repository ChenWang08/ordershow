# 订货排行按需查询调整（2026-10-31）

后续筛选器联动与未填写空值修正见[2026-11-01 验证记录](ranking-cascade-2026-11-01.md)。下文保留当时的查询/负载结果，不代表后续联动选项 SQL 的性能。

## 范围

按直播订货场景调整四维排行：优先保证订单提交，领导需要看时才确认查询。客户类型、大区、项目组单选，品种多选；金额榜与吨数榜、手动确认/刷新、同一明细交集及 TopN 外总计均保留。

- 移除未发布的实时 `order_ranking_stat`、`order_ranking_product_stat` 表及其下单、改单、调价维护链路、回填工具。每次有效订单写入不再额外执行这三条汇总 SQL。
- 原 `order_dashboard_stat`（整单可计算吨数）和 `order_dashboard_product_line_stat`（项目组/礼盒金额与数量）照常维护和使用，原汇总开关不变。
- 活动进行中，未选商品条件使用订单头金额及原吨数汇总；选了项目组或品种则读取当前有效 `SUBMITTED` 订单的匹配明细。无需维护新的实时品种汇总。
- 选项只读取实际维度，不汇总金额/吨数。包含当前发布配置及有效订单保留快照，不硬编码名称。
- V044 只新增三个完整历史基础表；FINISHED 随管理员维护更新，ARCHIVED 冻结，重新开放清除冻结基础。历史基础用于保证今后任意组合仍能回看，与实时下单汇总不同。

本轮完成源码、隔离测试和文档，并按用户要求提交到本地 Git；未部署业务 Docker、迁移业务库、发布镜像或推送。初版实时品种汇总的测试过程保留在[旧记录](ranking-filters-2026-10-31.md)，其中回填命令和部署步骤已失效。

## 查询与索引

先按活动、有效状态、客户类型和大区选中订单，再使用现有订单明细索引读取项目组/品种。实际执行计划发现 MySQL 可能先全扫明细再过滤客户，已通过限定连接顺序修正。没有额外新增在线订单/明细索引，避免给所有下单增加未经验证的维护成本。V044 历史表自带冻结查询索引。

匹配数据量由业务条件决定；索引和查询顺序帮助减少无关读取，不改变应统计的业务数量。宽范围商品条件仍需要读取较多明细。

## 规模与负载验证

规模用例为 3,000 单 × 200 商品 = 600,000 条当前明细，比较原汇总开关开/关的业务结果，记录实际 SQL 的 EXPLAIN ANALYZE。另测每个 SKU 独立品种，确认不依赖组合压缩率。

| 独立查询场景 | 样本数 | P50（毫秒） | P95（毫秒） |
| --- | ---: | ---: | ---: |
| 全部条件，保留原吨数汇总 | 20 | 46 | 49 |
| 仅项目组，按需明细 | 20 | 963 | 1001 |
| 四维金额，按需明细 | 20 | 105 | 109 |
| 四维吨数，按需明细 | 20 | 108 | 113 |
| 实际选项读取 | 10 | 961 | 987 |
| 每个 SKU 独立品种，四维 | 20 | 101 | 104 |
| 每个 SKU 独立品种，仅项目组 | 10 | 930 | 965 |

以上包含 Java 服务、事务与数据库往返，不含 HTTP，MySQL 测试实例没有 CPU 限额，不能与下文限额负载或旧报告直接作同环境对比。实际窄查询计划先定位 250 单，再通过原明细订单索引读取 50,000 行；宽项目组定位 3,000 单、读取 600,000 行。选项虽然不统计金额/吨数，仍需提取已下单明细的实际维度，进入也有约一秒读取成本。

HTTP 对照由 `tests/load/ranking-event-runner.mjs` 编排，固定独立项目 `order-show-load-ranking`、端口 8580，测试前后重建其专属数据库。使用相同初始客户、商品、会话和资源配置，对比初版“实时品种汇总”四维版本与本次“按需明细”版本的临时 JAR；两个版本均开启原汇总。此对照不代表本地已部署的旧固定排行版本。

- 3,000 个合成客户，初始 2,500 单 × 200 商品，含完整当前明细和对应历史版本明细。
- 100 个 H5 浏览会话及活动信息 SSE 连接；每人每 15 秒请求商品、当前订单，每 30 秒保存草稿，进入时间错开。
- 分别以每分钟 100、200 次固定到达率提交新订单，持续 2 分钟；每次含草稿、真实提交事务、确认读取。第 90 秒额外让 20 个客户同时开始下单流程，每人先保存草稿，再正式提交，正式提交请求有短暂先后。
- 每 15 秒偶尔查一次排行，轮换全量、宽项目组、四维金额和吨数。停止写入后各条件再采 20 次 HTTP 查询。
- 每次确认/刷新同时重新读取实际筛选选项，保持与当前页面的请求组合一致。
- 每轮从同一初始夹具重建数据库，顺序为旧100、新100、新200、旧200；核对订单头、明细、历史版本及原吨数汇总。
- 后端 2 CPU/1280 MiB（堆 768 MiB），MySQL 1.5 CPU/1 GiB，DB 连接池 60。全部是本机限额测试，不代表生产服务器容量。

### 提交结果

以下为实际订单提交 PUT 的延迟，草稿和确认 GET 单独计时，不是整个页面操作时长。每轮额外 20 单突发单独统计，不混入固定到达率提交的百分位。

P95 表示约 95% 的请求在该时间内返回结果。例如本次 200 单/分钟的常规提交 P95 约 73 毫秒，即 0.073 秒；20 个客户集中下单时，正式提交步骤 P95 约 510 毫秒，即 0.51 秒。两者均不包含前面的选商品、保存草稿或页面加载时间。

| 场景 | 常规提交样本数 | 提交 P50 / P95（毫秒） | 20 单突发提交 P95（毫秒） | 失败 / 对账差异 |
| --- | ---: | ---: | ---: | --- |
| 初版实时汇总，100 单/分钟 | 200 | 37 / 78 | 453 | 0 / 0 |
| 本次按需查询，100 单/分钟 | 200 | 36 / 64 | 457 | 0 / 0 |
| 初版实时汇总，200 单/分钟 | 400 | 36 / 68 | 577 | 0 / 0 |
| 本次按需查询，200 单/分钟 | 400 | 35 / 73 | 510 | 0 / 0 |

四轮共成功提交 1,280 单，主负载记录 12,304 次 HTTP 请求（含 400 次 SSE 建连），请求及内容校验均无失败。每轮 100 条 SSE 均成功建立并保持到测试结束。100 单/分钟场景最终 2,720 单、544,000 条当前明细、总金额 54,400,000、544 吨；200 单/分钟场景最终 2,920 单、584,000 条当前明细、总金额 58,400,000、584 吨。订单头/明细/版本头、原吨数及项目组汇总均对账一致，另有最新历史版本明细抽样读取通过。

旧版 200 档结束时有 2,920 个有效实时汇总标记、58,400 条品种事实，缺失或过期为 0，说明对照确实使用且维护了初版汇总。新版不存在两张实时品种汇总表，原汇总仍完整。

MySQL 累计插入行数在主负载前后之差：100 档初版 51,980 行、本次 47,360 行，少 4,620 = 220 × 21；200 档初版 98,780 行、本次 89,960 行，少 8,820 = 420 × 21。每单少的 21 行为该分布下的 20 条品种事实和 1 条版本标记。这是写入数量的差异，不能换算为整体 CPU 或耗时节省比例。四轮数据库行锁等待计数均未增加；5 秒监测采样中连接池等待、写入准入等待和草稿死锁指标均为 0，不能据采样排除瞬时排队。

### 查询代价

停止写入后，每条件采样 20 次 HTTP。200 档结束后的同规模数据对比如下：

| 条件 | 初版实时汇总 P95（毫秒） | 本次按需查询 P95（毫秒） |
| --- | ---: | ---: |
| 全部条件，原吨数汇总 | 61 | 57 |
| 仅项目组 | 178 | 943 |
| 四维金额 | 35 | 131 |
| 四维吨数 | 34 | 131 |

在真实混合负载及同时刷新选项时，按需方案宽项目组响应最慢约 2.22 秒，四维金额最慢约 358 毫秒、吨数约 228 毫秒；选项刷新也可到约 2.20 秒。这些混合查询每种每轮仅 2 次，只报告观测到的耗时，不用于推断稳定百分位。初版的对应商品查询更快，这是保留实时事实表换来的读优化。

### 结论与边界

两种方案均通过本次短时负载。常规提交 P95 有升有降，不能据此认定删表会稳定提速或降低整体数据库消耗。按需方案明确省去每次提交/修改的三条额外 SQL 及品种事实维护，降低实时写入和维护复杂度；商品条件和选项读取承担更多扫描成本，仍与下单共用 MySQL 资源。适用于本次选择的“现场偶尔查排行”方式；这次测试不构成生产容量或长时间稳定性承诺。

每轮只有两分钟，使用合成短名称、固定价格和品种分布。会话由夹具准备；不包含电话登录、真实浏览器渲染、商品图片下载、直播媒体或生产网络。旧汇总在该分布下每单 20 条事实，不能据此推断所有品种分布的写入成本。主负载中的 20 单突发与宽项目组查询未刻意安排在同一瞬间。

证据保留在本地忽略目录 `outputs/ranking-on-demand-*.log`、`outputs/ranking-on-demand-scale-results.json`、`outputs/load-ranking/`；负载编排日志为 `outputs/ranking-event-comparison.log`。原型测试脚本曾把最新版本也应立即复制历史明细作为断言，已按系统原延后复制规则修正后完整重跑；预检失败记录保留在 `outputs/ranking-event-preflight.log`，不计入上述最终结果。

全部测试通过后，临时容器、网络及 `order-show-load-ranking` 专属数据卷均已删除，`order-show-e2e` 临时数据库也已释放。业务服务和业务数据库没有部署或迁移。

此轮写入测量为首次提交新订单，不用其延迟推断大批改单、调价或结束冻结的耗时。初始订单预置完整历史明细；本次新增订单沿用原机制，在被下一版替代前由当前明细提供最新版本内容，对账及抽样历史读取按该机制检查。
