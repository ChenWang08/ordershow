# 抽奖候选 SQL 与订单变更审核锁：源码修复验证

日期：2026-11-06（北京时间）。状态：源码修改及隔离验证完成，未构建、推送或部署 ACK 交付镜像。

2026-11-09 补充：本记录中的审核并发检查直接调用服务层。后续核对发现，统一 HTTP 拦截器仍会先取活动排他锁，导致服务层共享锁优化未完整作用于真实入口。该遗漏及两类预览的锁范围已另行修复，并通过真实 HTTP/统一拦截器并发验证，见 [2026-11-09 记录](activity-write-lock-http-2026-11-09.md)。本记录的历史测试数据保留；`20261106.1` 镜像不包含后续入口修复。

## 触发条件与修改

UAT 活动 HD20261105019 的候选预览在开启 `excludePreviousWinners` 后约 8 秒返回 500，关闭后正常。手动浏览器的正式 draw 也出现约 8.18 秒 500。此前隔离 MySQL 已复现旧 SQL 将约 4980 个客户与 1692 个订单候选组合成约 843 万条中间结果，单独补中奖索引仍不能消除该执行计划。

### 候选查询

- `LotteryService.candidates` 仅在最终客户查询执行一次当前白名单、客户类型、签到和中奖排除条件。
- 有效订单先限制在当前活动、`SUBMITTED` 状态。无商品明细需求时直接关联订单总额、箱数、吨数；有商品筛选或吨数明细需求时汇总本活动订单的匹配明细。
- 移除重复的客户 CTE、无明细时重复的订单关联以及候选路径中的强制连接顺序。保留无订单客户在全部客户/签到等概率范围内的 LEFT JOIN 语义。
- 预览与正式开奖继续共用同一候选计算。排除仅针对本活动 `VALID` 中奖记录；首轮与重复中奖开关语义保持一致。
- `QueryTimeoutException` 转为 `503 LOTTERY_QUERY_TIMEOUT`，提示查询超时；日志含请求 ID、活动、轮次、范围、加权方式、排除开关及耗时。保留 8 秒语句保护；未修改全局 JDBC、池等待或连接预算。

### 订单变更审核

- 通过和驳回均先查申请所属客户，再按“活动共享锁 → 客户独占锁 → 幂等记录/申请/订单”的顺序执行，和 H5 客户写入使用相同顺序。
- 获取锁后重新读取活动状态，处理等待期间发生的调价、归档等操作。审批继续检查申请状态及订单版本；不同客户可并行，同一客户串行。
- 审核已有订单允许客户已不在活动有效白名单中；H5 仍要求有效客户。
- `byIdForUpdate` 先对申请表单独按 ID 加锁，再普通联表读取订单、客户、审核人显示信息，避免对展示关联行附加独占锁。
- 调价、后台直接创建/调整/作废及其他原有全活动操作继续使用原来的活动独占锁。审核优化的范围是订单变更申请的通过/驳回。
- 这些锁通过 MySQL 协调，不依赖单 JVM/单 Pod 内存锁。

## 规模验证

5000 个客户、1713 笔 SUBMITTED 订单，其中一个金额为零、按金额加权不具备资格；前两轮实际完成共 20 名中奖。

- 排除中奖后 SQL 返回 1693 行，Java 资格过滤后为 **1692 个候选**。
- 本地候选服务调用（含 JDBC 与 DTO/权重计算）实测 **63ms**。
- `EXPLAIN ANALYZE` 根节点约 **12.4ms**，没有旧计划中的 `join (no condition)` 百万级中间组合。
- 第三轮正式开奖成功，候选数 1692，最终 30 名有效中奖客户互不重复。
- 四种加权方式与商品筛选下，排除中奖后的金额、箱数、吨数及作废中奖记录行为均有真实 SQL 用例。

这些数据为定向隔离验证，不是 UAT HTTP P95，也不是 300 人完整混合压测结果。身份、Redis、存储等无关服务有替身；两个独立服务对象/数据库事务的并发证明锁不依赖服务实例，但不等同于真实多 Pod 压测。

原始日志位于忽略目录 `outputs/lottery-review-codefix-20261106/maven.log`、`boundaries.log`。其中故障注入与真实超时的错误/警告日志是预期测试路径，不是未通过的请求。
