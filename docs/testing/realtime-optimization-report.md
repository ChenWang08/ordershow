# 实时通知积压优化与验证（2026-09-08）

后续H5读取/批量写入及线程上限优化见[H5优化报告](h5-throughput-optimization-report.md)；本报告保留通知优化阶段的数据。

最终代码已更新至本机业务前后端，数据容器未替换，无新增数据库迁移。镜像备份与只读检查见[部署记录](../deployment/2026-09-08-realtime.md)。

## 改动

- 后端由每秒最多100条、逐条确认，改为每500ms最多8批、每批1000条；同一轮按活动合并成一次invalidate，按选中ID分批更新发布状态。
- 不按`id <= 最大值`确认，避免把未到期或晚提交事件误处理；一轮游标不跨轮保留，下一轮仍能读取更小的迟提交ID。
- 通知表示“重新读取活动快照”，内容不随事件数量线性膨胀。eventCount和oldestEventAt用于观察合并数量与延迟；保留最后事件字段兼容旧客户端。
- 网络发送不占用数据库事务。确认失败保留PENDING以便重试，可能重复invalidate，不承诺通知恰好一次；当前仍为单后端发布器。
- 断开的SSE订阅移除，空订阅组清理；对AsyncRequestNotUsableException不再向不可用流写JSON错误。另发现到期流抛出AsyncRequestTimeoutException，补充仅对text/event-stream返回空结果的处理；非流式超时仍返回503，普通异常仍返回500。
- 订单看板、排行和战报同一时刻只执行一个刷新，请求期间的通知合并为一次后续刷新；连接open时重新获取快照，15秒轮询兜底；旧活动/筛选的迟到响应不再覆盖新状态。

同样的后端2CPU/1280MiB、MySQL1.5CPU/1GiB、连接池20，构造12000条专属测试事件，分属两个活动，各6000条，连接100个SSE客户端。

| 指标 | 结果 |
|---|---:|
| 每条连接收到合并通知数 | 2 |
| 通知P95 / 最大延迟 | 1512 / 1513ms |
| 数据库确认最慢 | 2059ms |
| 其中10个看板API刷新最慢 | 2945ms |

全部12000条均发布，活动没有串流。较小ID但尚未到发布时间的哨兵保持PENDING，校验后只删除该条本次构造的测试哨兵；保留其余测试事件及报告。
订单、金额、数量、历史版本数量未变化。时间从数据库事件创建开始，包含测试插入事务时间；看板刷新为API完成，不包含浏览器渲染。
原始结果：outputs/load/notify-mts8fc8d.json。

## 持续高负载专项

预热20流程/秒、3分钟通过：3601次提交，读P95 5.62ms、写17.28ms，错误及丢弃迭代0。
随后确认100条SSE连接就绪，执行200用户高频混合负载5分钟，并持续观察通知6分钟。

- 100条连接全部保持，收到34500帧通知，每条345帧；第一条连接覆盖22292个事件，通知P95 1325ms、最大2022ms，无断连，通知专项通过。
- 高负载结束后待发布队列0；额外100连接探针P95 322.37ms、最大322.90ms。
- 订单负载完成22289次提交、新增22289版本、HTTP错误率0；读P95 760.59ms、写989.08ms。
- **200用户整体读取仍超过500ms门槛**，不能宣称200用户全部性能达标。本轮解决的是通知吞吐和刷新堆积，未增加服务器资源。

原始结果：mixed-200-1788846601893.json、sse-observe-1788846577914.json。
此前82.467秒记录与本次并非完全相同数据库快照/负载序列的严格A/B；本次包含更多历史数据及100个持续订阅者，分别记录实际条件。

## 保留的失败与边界

首次直接上200用户并建立大量连接的启动阶段，出现应用CPU饱和、连接池超时，约32秒中止；HTTP失败率2.01%，通知最长9090ms。未发现死锁证据，但没有单独证明所有饱和成因。
该失败记录保留，不用预热后的结果覆盖，也不宣称冷启动高压已解决。
中止时客户端记录545次成功、数据库实际591次提交。重放该运行的全部591个原幂等请求均成功，未增加订单/版本，金额数量不变；属于中止造成的部分响应未确认，不是重复订单。
原始记录：mixed-200-1788845744393及其replay-verification.json、sse-observe-1788845729999.json。

本轮没有重新执行千人场景或60分钟长稳；100个持续订阅者只接收通知，不等同于100个页面持续查询完整看板，10个看板刷新是独立突发专项。
不得把本轮通知指标当作瞬间千人下单或所有资源配置下的保证。

## 回归与复跑

- 前端85项测试及类型检查通过；队列测试包含1000次并发刷新触发、清理、迟到响应和失败恢复。
- 后端全套88项测试通过（含隔离API E2E和真实MySQL锁测试）；最终补充流到期处理后，12项相关定向用例通过，其中包含2项新增超时用例。未重复跑30分钟等待来触发流自然到期，而是通过对应异常处理回归验证。
- 后端测试覆盖跨活动合并、精确确认ID、迟提交低ID、空队列、确认失败重试、发送异常不确认、批次边界、断连清理及错误响应。
- 业务订单金额/数量/版本连续性、幂等、跨活动隔离和看板核对通过。
- `node tests/load/sse-backlog.mjs 12000 100`构造专属突发事件；`sse-observe.mjs 360 100`是只读订阅者，可与写负载并行，不污染提交版本对账。
- 连接测试中的延迟从oldestEventAt到客户端收取，包含订单事务提交前的时间；不提供Last-Event-ID重放，重连依靠快照恢复。

Spring断连异常行为参考：[AsyncRequestNotUsableException](https://docs.spring.io/spring-framework/docs/6.2.12/javadoc-api/org/springframework/web/context/request/async/AsyncRequestNotUsableException.html)。
