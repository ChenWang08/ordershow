## 交付状态

## 功能与口径

- 客户类型、大区、项目组单选；品种多选；默认全部。客户类型 `ALL` 表示不限类型，也包含不区分类型客户，不提供单独的空客户类型入口。
- 选项来自当前发布的有效白名单、商品目录及当前有效订单快照，不硬编码大区、项目组、品种名称。三个单选条件独立；综合、特渠、不区分类型均保存实际大区，也可留空。
- 大区、项目组、品种的空值独立编码。“其他”“ALL”或带逗号的名称可作为真实字段筛选。已下单身份和商品快照保留原记录；更改目录或白名单不会追溯改写订单。
- 进入只读取选项，不计算排行和金额/吨数。确认后应用条件与金额/吨数口径。手动刷新沿用最后成功确认的整套条件；重置和修改草稿均不发统计请求。
- 失败保留上次成功数据、条件说明和刷新时间。重复点击合并当前请求；切换活动取消旧请求并清空结果。
- 只读取 SUBMITTED 当前有效订单。待审核变更不替换有效明细，撤回、作废不统计。项目组和品种必须命中同一条明细；过滤商品后按匹配明细金额、数量、可计算吨数累计。顶部总计覆盖全部匹配订单，不受公司/分公司 TopN 限制。
- 金额和吨数排行均保留原排序次序。无可计算吨数的客户不进入吨数榜；有效零吨可参与。部分明细缺吨箱系数时仅累计可计算部分，顶部吨数没有可计算值时为 0。
- 排行使用独立 `RankingService`。综合看板 TOP15 保持 `/dashboard` 既有读取，不调用四维排行。共用少量基础存储/SQL 不意味着触发其他页面统计。
- 品种最多 500 项。较短条件使用 GET；编码筛选串超过 6000 字符自动使用同路径的只读 POST JSON，避免 URL 长度限制。

## 数据与历史

V044 新增按订单、项目组、品种分组的事实表及版本标记。正常业务在原订单事务内更新；版本与订单不一致或缺少汇总时，商品过滤按该订单当前明细回退。查询总计、榜单与版本来自同一条 SQL。

FINISHED 生命周期保存完整可筛选基础，管理员维护后同步更新；ARCHIVED 保存后冻结，任意新组合均查询冻结基础，不是从已截断 TopN 反推。重新开放时随旧展示快照清除新基础，恢复查询当前订单。

旧历史首次确认时，使用活动锁协调一次初始化；核对旧冻结总金额、数量、订单数、吨数及所有已保留榜单，成功后才建立新基础，旧快照仍保留。差异返回 `RANKING_HISTORY_MISMATCH`，事务回滚，不覆盖历史。旧版没有保存完整商品维度历史，因此核对只能证明旧总计及已保留榜单一致，无法证明从未被记录的维度分布；旧历史首次选项暂读保留资料。上线前应利用备份核查有疑问的归档活动，不能用当前目录重算替代冻结数据。

## 验证方式

- 前端完整自动化测试、类型检查、构建和修改文件规范检查。
- 浏览器使用真实 React、页面样式及合成 HTTP 响应，不连接业务 API；检查进入无统计请求、确认、草稿与已生效条件分离、金额/吨数、逗号品种多选、失败保留、重置、1920/1440/768/440 宽度以及下拉框遮挡和越界。
- MySQL 实际执行四维查询，对比原始明细、缺失汇总、有效汇总及版本失效回退；验证空值、同一商品行交集、TopN 外总计、历史冻结、并发首次历史初始化和回填对账。
- 执行旧排行、基础汇总、综合看板页面读取回归，验证 TOP15 等页面路径。
- 另用完整 Flyway 链从 V043 升级 V044，核对订单/明细不变，验证各类型客户的导入、手动新增/编辑大区及结束后维护刷新。

运行日志位于本地 `outputs/ranking-*.log`，浏览器截图在 `outputs/ranking-filters/`。这些合成测试产物默认不纳入 Git。

最终结果：前端 335 项通过，类型检查、构建和修改文件规范检查通过；真实浏览器四种宽度通过。后端最终回归集合共 323 项：260 项已验证通过，63 项按环境开关跳过；其中完整升级用例初次因合成商品缺少可下单价格而失败，补全测试数据后单独重跑通过（`ranking-migration-tests.log`），其余 259 项在 `ranking-backend-final.log` 中通过。此前含 60 万明细及并发测试的完整批次为 268 项通过、54 项跳过（`ranking-backend-tests.log`）。未运行需要完整 HTTP/Redis/对象存储栈的端到端套件，不把浏览器合成接口验证计为端到端通过。

## 大数据量与并发

固定测试数据库中生成 3,000 张订单 × 200 条商品 = 600,000 条真实 MySQL 明细。常规样本共 20 种项目组/品种组合，合并为 60,000 条分组事实；另测 200 个独立品种，分组后仍有 600,000 条事实的低压缩情形。四维条件匹配 250 单；金额与原始明细查询一致。

并发场景使用与正式下单相同的 READ_COMMITTED 写事务，4 个写任务各执行 25 次更新，3 个读任务各执行 20 次查询。覆盖订单头、明细与汇总的原子更新，完成后总金额和逐单事实对账一致。首轮测试曾因测试写事务默认 REPEATABLE_READ 在空汇总区间产生间隙锁死锁；核查正式 OrderService 使用 READ_COMMITTED 后，测试改为与正式代码一致，无添加重试掩盖错误。

实测耗时如下，单位毫秒，P95 为样本第 95 百分位；原始查询仅 5 次，P95 即最慢样本，不能据此作严格容量推断。

| 场景 | 样本数 | P50 | P95 |
| --- | ---: | ---: | ---: |
| 原始明细，仅项目组 | 5 | 1099 | 1170 |
| 原始明细，四维条件 | 5 | 121 | 136 |
| 汇总，全活动金额榜及总计 | 20 | 59 | 68 |
| 汇总，仅项目组 | 20 | 317 | 400 |
| 汇总，四维金额榜 | 20 | 43 | 47 |
| 汇总，四维吨数榜 | 20 | 44 | 48 |
| 选项读取 | 10 | 101 | 103 |
| 3 读与 4 写同时进行，读 | 60 | 72 | 81 |
| 同上，订单更新含两类汇总维护 | 100 | 52 | 67 |
| 低压缩，四维条件 | 20 | 117 | 142 |
| 低压缩，仅项目组 | 10 | 2247 | 2367 |

常规样本新事实分批回填耗时约 96 秒。低压缩项目组查询仍可能超过两秒，说明过滤返回更少不等于所有条件都快；商品组合分布、匹配覆盖范围和实际执行计划均影响成本。

耗时包含 Java 读取方法、数据库往返及事务开销，不含浏览器、HTTP、鉴权、Redis、对象存储、完整下单流程；样本不代表生产容量、长时间稳定性或所有品种分布。没有用旧容量报告替代本次结果，也没有把返回行数减少当成扫描量必然减少。

## 后续部署准备（本轮未执行）

1. 备份目标业务数据库，确认 V044 与待发布的其他迁移版本顺序；先在目标环境隔离副本验证，确认旧归档资料可核对。
2. V044 只建新表，不在迁移中全量回填。旧订单可以按原始明细回退，但建议在开启汇总前分批准备并对账。
3. 现有 `scripts/dashboard-summary.ps1` 新增 `ranking-rebuild` 和 `ranking-check`，显式指定 Compose 文件、项目和活动；每次最多 200 单、每单独立短事务，可通过 `AfterOrderId` 继续。仅维护新派生事实，不修改原订单或冻结历史。
4. 原整单吨数汇总仍服从既有开关规则；关闭期间有写入或裸 SQL 修改时，重新开启前同时执行原 `repair/check` 和新 `ranking-rebuild/ranking-check`，不能只回填新表。裸 SQL 不增加订单版本也不受版本校验保护。
5. 回退优先切回旧应用版本，保留 V044 表及冻结基础供核查；不要直接回滚旧数据库备份覆盖上线后订单。删除新表须先备份，确认没有新代码访问；新冻结基础不能随意清除，清除后无法保证历史恢复。

索引帮助定位每单和品种组合，不改变业务匹配总量；全部条件或品种覆盖面大时仍需要读取较多数据。分组事实和历史基础增加写入、存储和结束活动时的工作量，需结合目标服务器监测安排回填和容量验收。
