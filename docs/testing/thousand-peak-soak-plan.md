# 千人峰值与60分钟长稳执行说明

使用优化后的独立order-show-load环境，API端口8280；业务order-show环境不参与负载。
保留原后端2CPU/1280MiB、MySQL1.5CPU/1GiB、连接池20限制。k6使用2CPU/1GiB。

## 场景和门槛

1. 20名独立客户完成进入/首次下单冒烟，各10秒；使用独立的20名客户，不消耗正式千人样本。
2. 高频混合操作按200→500→1000用户，每档5分钟，每次流程暂停1秒。每档失败停止该模型的升压，并核对数据。
3. 千人集中进入：1000个不同客户，在60秒内按固定速率完成真实手机号验证和商品查询；查询使用验证响应中的新Cookie/CSRF。
4. 千人集中首次下单：另外保留未下单状态的同一批1000客户，在60秒内分别创建首单并读取确认。不是重复使用一个客户，也不是瞬间1000个在途请求。
5. 两项千人场景通过后，在20完整流程/秒下先跑3分钟，再执行60分钟长稳（100个可用执行VU，轻量订单响应）。这不是1000活跃VU持续60分钟。
6. 长稳前后执行100条SSE连接的通知专项；没有保持100条SSE连接整整60分钟。最后核对订单/版本/看板，保留结果并停止测试服务。

高频连续操作与一分钟内1000人各操作一次是不同负载模型，分别判定；前者超标不等于后者不能独立测试。
若出现数据正确性错误立即停止全部负载。千人场景或长稳预检失败，不启动60分钟阶段。

读P95≤500ms、写P95≤1500ms、P99≤3000ms、正常请求错误率<1%。千人场景还要求完成客户数严格等于1000、丢弃迭代为0、业务载荷断言全部通过。
千人首单最终应新增1000笔订单/版本，总金额2000000元（每单10商品×2箱×100元）。
长稳要求配置60分钟、完成至少72000次完整流程、丢弃迭代为0，并核对成功提交数等于新增历史版本数。
计时复核说明：初版脚本直接要求统计窗口≥3600000ms。本轮配置60m、完成72000次，但统计窗口为3599828.69356ms，产生171.30644ms的边界误报。复核规则保留原始值，允许不超过1秒的统计时钟边界差，同时仍必须完成全部计划迭代；更短配置、少迭代或超过容差均拒绝。原始失败记录不覆盖，复核结果另存analysis.json，测试附加了该边界及不完整运行的回归用例。

## 运行及结果

环境启动并健康后执行：
```powershell
node tests/load/thousand-soak.mjs
```

首次运行需要至少1020个未下单的LOAD-1客户。峰值样本会被保存为outputs/load/peak-fixture.json及时间戳归档；它包含仅测试环境有效的会话，不应提交。
完成过首单的客户不可直接复用来重跑首次下单场景，准备脚本会检查可用人数；不要通过清空业务库获得新样本。

每阶段生成k6汇总、资源采样、数据库前后快照和对账文件。每30秒更新`*-progress.json`，每5秒追加`*-samples.jsonl`，方便长时间运行时检查进度及保留部分证据。
整套执行清单为`thousand-soak-时间戳.json`。最终报告区分通过、超标、未执行，不以已发送HTTP请求成功率掩盖未启动的迭代。
全部仍属于本机API测试，未覆盖真实手机、前端资源下载、浏览器渲染和正式云环境网络入口。

查看长稳进度：`node tests/load/watch.mjs 运行ID`。结束后复核：`node tests/load/analyze-soak.mjs 运行ID`。

速率调度参考：[k6 constant-arrival-rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/)。
